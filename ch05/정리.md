# ch05. 지표 모니터링 및 경보 시스템

## 핵심 요약

1. **부하는 사용자 수가 아니라 서버 수 × 지표 수가 정한다.** 서버 풀 1,000개 × 100대 × 지표 100개 = 시계열 천만 개이고, 10초마다 재면 초당 100만 건을 쉬지 않고 쓴다. 읽기는 대시보드와 경보가 일으키고 장애가 나면 몰렸다 사라진다. 보통 웹 서비스와 반대로 쓰기가 압도적이라 시계열 DB(InfluxDB, 프로메테우스)를 쓰고 수집기와 DB 사이에 카프카를 둔다. DAU 1억은 계산에 한 번도 쓰이지 않는다.
2. **시계열 하나는 "이름 + 레이블 전부"로 정해지고, 시계열 DB는 레이블에서 시계열을 찾는 역색인을 둔다.** 관계형 DB는 값 하나를 넣을 때마다 레이블 인덱스를 고치지만, 시계열 DB는 새 시계열이 생길 때만 고치고 값은 그 시계열 끝에 붙인다. 그래서 레이블 값의 가짓수(카디널리티)가 낮아야 한다. user_id를 레이블로 쓰면 사용자마다 시계열이 생겨 이 장점이 사라진다.
3. **잃었을 때 피해가 클수록 보호 장치가 무겁다.** 값 몇 개는 빠져도 된다(카운터는 서버가 누적값을 들고 있어 다음 값에 빠진 증가분이 들어 있다). DB가 멈춘 몇 분 동안의 값은 카프카에 쌓아 둔다. 경보는 상태를 기록하고 카프카를 거쳐 최소 한 번 전달한다.

## 설계 정리

```
쓰기 경로 (늘 바쁨)
  지표 출처
    │  풀: 수집기가 /metrics를 가져감 (대상은 서비스 탐색, 수집기끼리는 해시 링 + 가상 노드로 나눔)
    │  푸시: 같은 서버의 에이전트가 묶어서 로드밸런서로 보냄
    ▼
  지표 수집기 클러스터 (자동 확장)
    ▼
  카프카 (키: 지표 이름, 또는 이름 + 일부 레이블)   <- DB가 멈춰도 여기 남음
    ▼
  소비자 (플링크 등. 저장 전에 집계할 수도 있음)
    ▼
  시계열 DB (인코딩과 압축, 다운샘플링: 원본 7일 -> 1분 단위 30일 -> 1시간 단위 1년, 냉동 저장소)

읽기 경로 (가끔 몰림)
  시각화(그라파나) --질의--> 질의 서비스 + 캐시 --> 시계열 DB   (질의의 85%가 최근 26시간)
  경보 관리자 --1분마다 규칙 질의--> 질의 서비스
    │  조건을 넘으면 (up == 0 이 for 5m 동안)
    ▼
  경보 저장소 (상태: 대기, 발령, 해결) -> 카프카 -> 경보 소비자 -> 이메일, SMS, 페이저듀티, 웹훅
```

풀과 푸시는 지표 종류가 아니라 "수집하는 쪽이 찾아갈 수 있느냐"로 고른다.

| | 풀 (프로메테우스) | 푸시 (클라우드와치, Datadog Agent) |
|---|---|---|
| 연결을 여는 쪽 | 수집기가 서버로 | 서버가 수집기로 |
| 유리한 점 | 디버깅(`curl /metrics`), 상태 진단(`up`), 신빙성(목록에 있는 서버만) | 수명이 짧은 작업, 방화벽, 어디서든 보낼 수 있음 |
| 쓰는 곳 | 같은 네트워크에서 목록을 아는 서버(쿠버네티스) | 브라우저, 서버리스, 배치 작업, 외부 SaaS |

집계는 에이전트, 수집 파이프라인, 질의 시점 순으로 일찍 할수록 싸고 빠르지만 나중에 다른 질문을 할 수 없다. 실무는 원본을 두고 질의할 때 계산하되, 자주 묻고 무거운 계산만 recording rule로 미리 해 둔다.

## 토론하고 싶은 것

- 카프카를 넣을 것인가. 책은 카프카와 고릴라(큐 없이 쓰기 가용성을 지키는 DB)를 둘 다 제시한다. 실제 프로메테우스는 `remote_write`가 자기 디스크 로그(WAL)를 큐처럼 쓰고, Alertmanager도 카프카 없이 여러 대를 두고 서로 맞춘다. 면접에서는 어느 쪽으로 답할지
- 질의 서비스를 둘 것인가. 결합도를 낮추고 캐시를 두는 이점과, 그라파나 플러그인을 못 쓰게 되는 대가. Thanos와 Mimir처럼 프로메테우스와 같은 API로 말하게 하면 둘 다 얻는다
- 어디까지를 지표로 둘 것인가. 사용자 한 명 한 명의 기록은 카디널리티 때문에 지표가 아니라 로그나 분산 추적으로 보는데, 각자 회사에서는 경계를 어디에 두는지
- 풀과 푸시를 각자 어떻게 섞어 쓰는지. Datadog Agent는 서버 안에서는 `/metrics`를 끌어오고 MySQL에 물어본 뒤, 밖의 Datadog으로는 밀어 보낸다

## 더 찾아본 것

- 다운샘플링은 값을 골라 버리는 것이 아니라 구간의 값을 대표값 하나로 합치는 것이다. 평균만 남기면 잠깐 튄 값이 묻혀서, Thanos는 구간마다 개수, 합계, 최솟값, 최댓값을 함께 저장한다.
- 해시 링에서 수집기 위치는 ID의 해시로 정해져 구간이 들쑥날쑥하다(5대가 8, 13, 15, 60, 92에 떨어지면 45대와 2대를 맡는다). 그래서 수집기 하나를 `A#1`, `A#2`처럼 여러 번 해시해 점을 수백 개 올린다(가상 노드). 카산드라는 1.2 전까지 이 위치(토큰)를 손으로 정해서 노드를 늘릴 때마다 옮겨야 했다.
- 표 5.3의 "푸시는 보통 UDP"는 StatsD 시절에 가까운 이야기다. 지금은 클라우드와치 `PutMetricData`, Datadog Agent에서 Datadog으로 가는 구간, OpenTelemetry OTLP 모두 HTTP(TCP)다. UDP는 앱을 막지 않으려고 같은 서버의 에이전트까지만 쓰는 경우가 많다.
- 책에서 걸러 읽을 곳
  - 사례 2(164쪽)의 여섯 줄은 타임스탬프가 모두 같다. "지난 10분간"의 예라면 시각이 달라야 한다.
  - 행 프로토콜은 InfluxDB의 형식 이름이다. 프로메테우스는 `cpu_load{host="webserver01"} 50`, OpenTSDB는 `put cpu.load 1613707265 50 host=webserver01` 꼴이라 문법은 다르고, 공통인 것은 이름, 레이블, 타임스탬프, 값이라는 구성이다.
  - 지수 이동 평균 SQL(180쪽)은 실제로는 15분 칸 안의 누적 평균이다. 최근 값에 무게를 더 주는 계산이 없다.
  - Flux 예시는 초기 문법이다. 지금은 `from(bucket: ...)`, `exponentialMovingAverage(n: 10)`이고, Flux는 유지보수 모드이며 InfluxDB 3.x는 SQL(`date_bin`)로 돌아갔다.
  - 다운샘플링 예시의 30초 평균은 19, 25가 아니라 15.3, 26.7이고, "이중 델타" 그림은 차이를 한 번만 구한 것이다.
  - 경보 규칙 예시에는 맨 위 `groups:`가 빠져 있다.
- "질의의 85%가 최근 26시간"과 이중 델타 인코딩은 페이스북 고릴라 논문에서 나왔고, 프로메테우스의 압축도 이를 따랐다.
- 실제 Alertmanager에는 카프카도 카산드라도 없다. 프로메테우스가 경보를 Alertmanager 여러 대에 모두 보내고, Alertmanager끼리 가십으로 "이미 보냄" 기록을 나눠 중복을 막는다. 같은 묶음은 30초 모아 한 번 보내고(`group_wait`), 계속 발령 중이면 4시간마다 다시 알린다(`repeat_interval`).
- [Gorilla: A Fast, Scalable, In-Memory Time Series Database](https://www.vldb.org/pvldb/vol8/p1816-teller.pdf), [Prometheus 문서: Alertmanager](https://prometheus.io/docs/alerting/latest/alertmanager/)
