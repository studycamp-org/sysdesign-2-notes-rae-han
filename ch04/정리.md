# ch04. 분산 메시지 큐

## 핵심 요약

1. **카프카는 읽어도 지우지 않는 로그다.** 메시지를 파일 끝에 이어 쓰기만 하고 보관 기간(기본 7일) 동안 남긴다. 그래서 여러 서비스(소비자 그룹)가 같은 메시지를 각자 읽고, 필요하면 다시 읽는다. 디스크에 두는데도 빠른 것은 이어 쓰기만 하고, 방금 쓴 메시지는 페이지 캐시(메모리)에서 읽기 때문이다.
2. **토픽을 키로 나눠(파티션) 여러 브로커에 두고, 파티션마다 사본 3개를 서로 다른 브로커에 둔다.** 같은 키는 같은 파티션으로 가서 순서가 지켜진다. 생산자는 `acks=all`로 ISR(리더를 따라잡은 사본 명단) 전부가 받을 때까지 기다리고, 토픽은 `min.insync.replicas=2`로 명단이 하나만 남으면 쓰기를 거부한다. 잃느니 멈추는 쪽을 고른 설정이다.
3. **메시지 전달 방식은 "했는지 확실하지 않을 때 다시 하느냐"로 갈린다.** 오프셋을 처리 전에 저장하면 빠질 수 있고(최대 한 번), 처리 후에 저장하면 두 번 처리될 수 있다(최소 한 번). 정확히 한 번은 처리와 기록을 한 트랜잭션으로 묶거나, 덮어쓰기처럼 두 번 해도 결과가 같은 처리로 만든다. 소비자 쪽은 우리가 직접 만들어야 한다.

## 설계 정리

```
생산자 (주문 서비스)
  │  배치표(메타데이터)를 캐시해 두고 파티션 리더 브로커에 직접 보냄
  │  키 42 -> hash(42) % 3 = 주문-0,  acks=all
  ▼
브로커 1~4 (클러스터)                         컨트롤러 (KRaft)
  주문-0: 리더 B1, 사본 B2, B3                  메타데이터 관리
  주문-1: 리더 B2, 사본 B3, B4                  브로커가 죽으면 ISR에서 새 리더를 뽑음
  주문-2: 리더 B3, 사본 B1, B4
  사본은 리더에서 가져가 따라잡음. ISR이 모두 가진 마지막 오프셋(합의 오프셋)까지만 소비자에게 줌
  │
  │  풀(롱 폴링)로 가져감
  ▼
소비자 그룹 = 서비스 (그룹끼리는 모두 받고, 그룹 안에서는 파티션을 나눠 맡음)
  정산: 서버1 = 주문-0, 1  /  서버2 = 주문-2
  알림: 서버1 = 주문-0  /  서버2 = 주문-1  /  서버3 = 주문-2
  오프셋은 그룹마다 정해진 코디네이터 브로커가 __consumer_offsets 토픽에 저장
```

학교에 빗대면 이렇다.

```
학교 = 클러스터         선생님 = 브로커          교무부장 = 컨트롤러 (장부 = 메타데이터)
책 = 토픽               권 = 파티션             쪽 번호 = 오프셋
원본, 베낀 것 = 리더, 사본                     다 따라 베낀 선생님 명단 = ISR
반 = 소비자 그룹        학생 = 소비자           반장 = 그룹 리더 (권을 학생에게 나눔)
담임 = 코디네이터 (출석 체크 = 하트비트, 진도표 = 커밋된 오프셋, 다시 나누기 = 재조정)
```

전달 방식은 약을 먹고 달력에 체크하는 순서와 같다.

| 방식 | 순서 | 중간에 죽으면 | 정산 예 (주문 42, 1만 원) |
|---|---|---|---|
| 최대 한 번 | 체크 먼저, 약 나중 | 약을 안 먹음 | 1만 원 누락 |
| 최소 한 번 | 약 먼저, 체크 나중 | 약을 두 번 먹음 | 2만 원 |
| 정확히 한 번 | 요일별 약통 (꺼내는 것이 곧 기록) | 두 번 먹지 않음 | 1만 원 |

## 더 찾아본 것

- 카프카 4.0은 주키퍼를 없애고 컨트롤러가 KRaft로 메타데이터를 관리한다. 책의 주키퍼 설명은 그 전 방식이다.
- 책의 재조정은 그룹 리더(소비자)가 파티션을 나누는 classic 프로토콜이다. 카프카 4.0의 KIP-848은 코디네이터가 직접 나눠 하트비트 응답으로 알려 준다. 배포할 때는 SIGTERM에서 `close()`를 불러야 45초(`session.timeout.ms`)를 기다리지 않고 바로 재조정된다.
- 사본이 ISR에 드는 기준은 메시지 개수(`replica.lag.max.messages`)가 아니라 시간(`replica.lag.time.max.ms`, 30초)이다. 0.9에서 바뀌었다. 개수 기준이면 큰 묶음이 들어올 때마다 멀쩡한 사본이 명단을 들락거렸다.
- `acks`는 0, 1, all뿐이라 책의 "k개의 ISR"은 고를 수 없다. `acks=all`은 "2개면 답"이 아니라 ISR 전부를 기다리고, 2라는 하한은 `min.insync.replicas`가 맡는다. 책은 최소 한 번에 ACK=1도 된다고 했지만 `acks=1`은 답한 직후 리더가 죽으면 잃는다.
- 카프카 3.0부터 생산자 기본값은 `acks=all`과 멱등 생산자(`enable.idempotence=true`)다. 생산자에서 브로커까지의 중복은 브로커가 번호를 보고 버린다.
- 브로커가 죽어도 카프카는 다른 브로커에 사본을 자동으로 다시 만들지 않는다(책 그림 4.28과 다르다). 대부분 재시작이라 금방 돌아오는데 그때마다 수 TB를 복사하면 손해라서다. 운영자나 Cruise Control이 재배치하고, 재배치는 새 사본을 먼저 만들고 따라잡은 뒤 옛 사본을 지운다.
- 파티션은 늘릴 수만 있고 줄일 수 없다. 늘리면 같은 키의 새 메시지가 다른 파티션으로 가서 순서가 깨질 수 있다. 생산자가 소비자보다 먼저 새 파티션에 쓰면 `auto.offset.reset=latest`(기본값)인 그룹은 그 메시지를 건너뛴다.
- 책 149쪽 "생산자 그룹은 재조정 작업을 개시해야 한다"는 소비자 그룹이 맞다. 생산자에는 그룹도 재조정도 없다.
- 오프셋도 그룹이 비어 있으면 7일(`offsets.retention.minutes`) 뒤 지워진다. 오래 멈출 수 있는 그룹은 `earliest`로 둔다.
- [Kafka 문서: Replication](https://kafka.apache.org/documentation/#replication), [KIP-848: The Next Generation of the Consumer Rebalance Protocol](https://cwiki.apache.org/confluence/display/KAFKA/KIP-848%3A+The+Next+Generation+of+the+Consumer+Rebalance+Protocol)
