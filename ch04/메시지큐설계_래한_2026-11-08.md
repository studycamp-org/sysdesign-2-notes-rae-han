# 4장 분산 메시지 큐 - 래한, S1 로그창고

## 1. 전제

| 핵심 숫자 | 값 | 계산식 |
|---|---|---|
| 피크 쓰기 처리량 | 1.5GB/s (150만 건/s) | 50만 건/s × 1KB × 3 |
| 필요한 파티션 수 | 150 (넉넉히 300) | 처리량 1.5GB/s ÷ 10MB/s, 소비자 150만 건/s ÷ 1만 건/s |

- **교재와 다른 제약**: 로그 0.1% 이하 유실은 허용, 대신 생산자(서비스 서버)가 느려지면 안 된다

## 2. 결정 4개

| # | 결정 | 질문 | 내 선택 | 근거 (한 줄) | 감수한 것 |
|---|---|---|---|---|---|
| Q1 | 규모 | 피크 처리량, 2주 저장량, 파티션 수는? 무엇이 먼저 한계에 닿나? | 피크 1.5GB/s, 2주 2.1PB, 파티션 150 이상(넉넉히 300) | 브로커 수는 디스크(16대)와 네트워크(4대) 중 큰 쪽, 여기선 디스크가 정한다 | 브로커 장애 시 수십 TB 재복제. 압축, 계층형 저장소로 줄인다 |
| Q2 | 파티션 키, 생산자 전송 | ① 로그를 어느 파티션에 넣고 순서는 어디까지 지키나? ② 생산자는 어떻게 보내나? | ① 키 없음(고르게 분산) ② 수집 에이전트가 버퍼에 모아 일괄 전송 + 압축 | 로그라 고르게 넣고 순서는 찍힌 시각으로 맞춘다. 처리량이 최우선이고 서비스는 파일에만 쓴다 | 같은 서버 로그의 순서 보장 없음. 버퍼가 차면 오래된 로그를 버린다 |
| Q3 ★ | 복제와 ACK | 사본을 몇 개로 어디에 두고, 생산자는 언제 ACK를 받나? 소비자는 어느 사본에서 읽나? | 미진행 | | |
| Q4 | 소비 방식, 전달 보장 | (돌발: 장애로 로그 10배, 이상 탐지 지연 20분) ① 소비자는 어떻게 받고 그룹은 어떻게 나누나? ② 전달 방식과 오프셋 커밋 시점은? | 미진행 | | |

> 바뀐 결정: Q2 ① 서버 ID 키 -> 키 없음 (대화 중 핫 파티션 이야기)
