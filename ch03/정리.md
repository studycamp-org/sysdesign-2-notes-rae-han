# ch03. 구글 맵

## 핵심 요약

1. **위치 서비스와 경로 안내 서비스를 나눈다.** 위치는 최대 100만 QPS의 가벼운 쓰기이고 경로는 적은 수의 무거운 계산이라 따로 늘려야 한다. 위치 쪽이 느려져도 경로 안내는 살아 있어야 한다. 내비는 서버가 내 위치를 몰라도 돌아가고, 서버가 위치를 모으는 것은 교통 상황, 도로 탐지처럼 다른 사용자를 위해서다.
2. **지도는 고정 격자로 미리 그린 타일을 CDN으로 준다.** 같은 칸이면 누가 요청하든 URL이 같아 캐시가 된다. 요청마다 그 위치에 맞춰 그리면 캐시가 안 된다.
3. **길 찾기와 시간 계산을 나눈다.** 최단 경로 서비스는 교통을 보지 않고 도로 길이로 k개를 뽑고(그래서 캐시가 된다), ETA 서비스가 교통을 반영하고, 순위 결정이 거른다. 출발한 뒤의 변화는 적응형 ETA가 찾아 웹소켓으로 알린다.

## 설계 정리

```
보내기  단말 --POST (15초 묶음, keep-alive)--> 위치 서비스 --> 카산드라 (user_id, timestamp)
                                                    └--> 카프카 --> 교통량 DB, 경로 안내 타일 갱신, 개인화, 분석
경로    단말 --> 경로 안내 서비스 --> 지오코딩 (레디스)
                               └--> 경로 계획 --> 최단 경로 (A*, 타일, k개) --> ETA (ML) --> 순위 결정
지도    단말 --> CDN --> 원본 (S3, 미리 그린 타일)
받기    단말 <--웹소켓-- 적응형 ETA, 경로 변경
```

보내기(HTTP)와 받기(웹소켓)를 나눈 것은 2장에서 무상태 API 서버와 유상태 웹소켓 서버를 나눈 것과 같은 판단이다.

## 토론하고 싶은 것

- **경로 후보를 도로 길이로만 고르면** 교통까지 따진 가장 빠른 길이 k개 밖에 있을 수 있다. k를 늘릴까, 탐색에 교통을 넣을까? 실제 서비스는 탐색에 넣는다. 전처리를 "영역 나누기"와 "가중치 채우기"로 나눠, 교통이 바뀌면 가중치 채우기만 1초 안에 다시 한다(Bing Maps의 CRP, OSRM의 MLD).
- **타일을 다시 그리면 캐시는?** 지도 전체에 버전 하나(`/v124/9q9hvu.png`)면 앱이 혼자 URL을 만들지만 도로 하나만 바뀌어도 전체 캐시가 빈다. 타일마다 내용 해시(`/9q9hvu.a3f9.png`)면 바뀐 칸만 바뀌지만 앱이 해시를 몰라 지도 타일 서비스에 물어야 한다. 그 응답도 칸을 다시 그릴 때까지 같아서 캐시된다.
- **적응형 ETA의 상위 타일 검사가 놓치는 경우.** 책은 "바뀐 칸이 내 마지막 칸(출발지와 목적지를 둘 다 포함하는 가장 작은 칸) 안에 있나"만 본다. 가까운 길인데 고속도로 레벨의 큰 칸에서 사고가 나면, 큰 칸은 작은 칸 안에 들어갈 수 없어 걸러진다. 지오해시 접두어를 양쪽으로 봐서 "겹치나"로 확인하고, 후보는 경로 칸 집합(2차)과 ETA 재계산(3차)으로 다시 본다. 앞 단계는 놓치지 않게, 판단은 마지막에 한다.

## 더 찾아본 것

- 번역문의 "O(m)으로 줄어든다"는 O(n)이 맞다. 사용자마다 마지막 칸을 한 번씩 본다.
- keep-alive는 HTTP/1.1부터 기본이다. Node 서버는 쉰 지 5초(+1초) 만에 연결을 닫아서 ALB(60초) 뒤에서 가끔 502가 난다. `keepAliveTimeout`을 ALB보다 길게 잡는다(Node 27부터 기본 65초).
- 구글은 2010년 안드로이드 구글 맵 5.0에서 PNG 타일을 벡터로 바꿨고, 데이터가 100분의 1 이하로 줄었다. 책의 2단계 설계와 100PB 추정은 그 전 방식이다.
