# 시나리오 카드

각 시나리오는 교재 기준안(내부용 인프라 운영 지표만 / 서버 10만 대 · 서버당 지표 100개 / 수집 주기 10초 / 보관 1년: 7일 원본 → 30일 1분 해상도 → 1년 1시간 해상도 / 이메일·전화·페이저듀티·웹훅 알림 / 로그 모니터링·분산 추적 제외)과
일부러 다른 제약을 하나 이상 넣어서, 같은 질문이라도 다른 선택이 정당화되도록 만들었다.

목록을 보여줄 때는 `한 줄 요약`만 보여준다. 고른 뒤에 카드 전체를 보여준다.

계산 공통 가정(카드에 따로 없으면): 하루 ≈ 10⁵초, **데이터 포인트 1개 ≈ 16바이트**(타임스탬프 8 + 값 8, 압축 전. 지표 이름·레이블은 시계열마다 색인에 한 번만 둔다), 사본은 따로 곱한다.
**활성 시계열 수** = 출처(서버·파드·장비) 수 × 출처당 지표 수(레이블 조합 포함). **초당 데이터 포인트** = 활성 시계열 수 ÷ 수집 주기(초).
다운샘플링하면 하루 저장량이 `수집 주기 ÷ 새 해상도` 배가 된다(10초 → 1분이면 1/6, 10초 → 1시간이면 1/360).

---

## S1. 사내서버 — 사내 데이터 센터 인프라 모니터링  (입문 / 교재와 가장 비슷함)

**한 줄 요약**: 한 데이터 센터의 서버 2만 대에서 CPU·메모리·디스크 같은 운영 지표를 모아 대시보드와 경보로 쓴다. 서버는 거의 고정이고 팀마다 자기 지표를 자유롭게 추가한다.

| 항목 | 값 |
|---|---|
| 지표 출처 | 물리 서버·VM **2만 대**. 한 달에 몇백 대 정도만 추가·교체 |
| 지표 | 서버당 **200개**(OS 지표 + 각 팀이 직접 넣은 서비스 지표) |
| 수집 주기 | **10초** |
| 보관 | **1년** (교재와 같음: 7일 원본 → 30일 1분 → 1년 1시간) |
| 네트워크 | 단일 데이터 센터, 사내망. 어디서든 서로 접근 가능 |
| 사용자 | 운영팀 대시보드, 온콜 엔지니어 경보(페이저듀티·메신저 웹훅) |
| 경보 | 규칙 약 **2,000개**. 발령까지 1~2분이면 충분 |

**설계 포인트**: 교재 기준안을 그대로 따라가도 되는 시나리오. 대신 **팀마다 레이블을 자유롭게 붙일 수 있다**는 점이 시계열 수(카디널리티)를 어디까지 키울 수 있는지 본다.

**돌발 상황**: "한 팀이 배포하면서 요청 지연 지표에 `user_id` 레이블을 붙였습니다. 활성 사용자 수백만 명만큼 시계열이 생겨 하루 만에 시계열 수가 **100배**로 늘었고, 시계열 DB의 색인 메모리가 부족해 질의가 수십 초씩 걸립니다. 경보 관리자의 규칙 평가가 주기 안에 끝나지 않아 경보가 5분씩 늦게 울립니다. 무엇을 바꾸나요?"

## S2. 컨테이너 — 쿠버네티스 위 오토스케일 서비스와 배치 작업  (동적 출처 / 짧은 수명 변형)

**한 줄 요약**: 파드 수만 개가 트래픽에 따라 수시로 늘고 줄며, 몇 분 만에 끝나는 배치 작업도 하루 수십만 번 돈다. 수집 대상 목록이 계속 바뀐다.

| 항목 | 값 |
|---|---|
| 지표 출처 | 평소 파드 **5만 개**(오토스케일). 하루에 새로 뜨는 파드 약 **50만 개**(배치 작업 포함) |
| 배치 작업 | 평균 실행 시간 **2분**, 짧은 것은 **20초**. 끝나면 파드가 바로 사라진다 |
| 지표 | 파드당 **300개** (레이블: 서비스, 파드 이름, 노드, 버전) |
| 수집 주기 | **15초** |
| 보관 | **30일** (7일 원본 → 30일 1분). 그 이상은 필요 없다 |
| 네트워크 | 클러스터 3개, 같은 클라우드 리전. 서비스 탐색은 쿠버네티스 API |
| 경보 | 서비스 단위로 걸고 싶다(파드 단위 경보는 소음) |

**설계 포인트**: 교재가 풀 모델에서 "서비스 탐색으로 해결"하고 넘어간 **출처 목록의 잦은 변화**와 **생존 기간이 짧은 프로세스**가 주인공이다. 파드 이름이 레이블에 들어가 **하루에도 새 시계열이 계속 생긴다**(활성 시계열 ≠ 하루 동안 생긴 시계열).

**돌발 상황**: "대형 할인 행사로 10분 만에 파드가 5만 → **20만 개**로 늘었습니다. 수집기가 15초 주기 안에 수집 대상을 다 돌지 못해 일부 파드의 지표가 비고, '데이터 없음' 경보와 파드별 CPU 경보가 동시에 **수천 건** 터져 온콜 엔지니어의 휴대폰이 멈췄습니다. 무엇을 바꾸나요?"

## S3. 엣지매장 — 전국 매장 장비 원격 모니터링  (방화벽 / 불안정한 네트워크 변형)

**한 줄 요약**: 전국 5,000개 매장의 POS·키오스크·냉장 장비 상태를 본사에서 본다. 매장은 방화벽 뒤에 있어 밖에서 들어갈 수 없고, 회선이 자주 끊긴다.

| 항목 | 값 |
|---|---|
| 지표 출처 | 매장 **5,000곳** × 매장당 장비 **50대** = 25만 대 |
| 지표 | 장비당 **100개** (CPU·온도·문 열림·결제 단말 상태 등) |
| 수집 주기 | **60초** (회선 비용 때문에) |
| 보관 | **1년** (교재와 같은 단계: 7일 원본 → 30일 1분 → 1년 1시간) |
| 네트워크 | 매장 → 본사 **아웃바운드만 허용**(방화벽·NAT). 매장 회선은 하루 몇 번 수 분~수 시간 끊김 |
| 본사 | 클라우드 두 리전에 수집 시스템 운영 |
| 경보 | 냉장 장비 온도 이상은 **10분 안에** 매장 관리자에게 문자. 회선 끊김과 장비 고장은 구분해야 한다 |

**설계 포인트**: 표 5.3의 "방화벽 등 복잡한 네트워크 구성" 행이 시나리오 전체를 지배한다. 회선이 끊기면 지표가 **늦게, 한꺼번에** 도착한다 → 데이터 집계 지점과 경보가 늦게 온 데이터를 어떻게 다루는지 본다. 수집 주기가 60초라 교재의 "30일 1분 해상도" 단계가 의미가 없어진다.

**돌발 상황**: "통신사 장애로 남부 지역 **800개 매장**의 회선이 2시간 끊겼다가 한꺼번에 복구됐습니다. 끊긴 동안 '데이터 없음' 경보 800건이 울렸고, 복구 순간 밀린 2시간 치 데이터가 동시에 올라오면서 '온도 이상' 경보가 이미 지나간 상황에 대해 또 울립니다. 매장 관리자들은 경보를 꺼 버리기 시작했습니다. 무엇을 바꾸나요?"

## S4. 결제SLO — 결제 플랫폼 SLO 경보  (낮은 경보 지연 / 사업 지표 변형)

**한 줄 요약**: 결제 플랫폼의 서버 지표와 함께 **초당 결제 실패율** 같은 핵심 지표를 1초 단위로 보고, 30초 안에 사람을 깨운다. 경보를 놓치면 돈을 잃는다.

| 항목 | 값 |
|---|---|
| 지표 출처 | 서버 **3,000대** |
| 지표 | 서버당 **500개**(10초 주기) + 핵심 SLO 지표 **1만 개 시계열**(결제 실패율, PG사별 응답 시간 등, **1초 주기**) |
| 보관 | **2년** (감사·분쟁 대응. 7일 원본 → 30일 1분 → 2년 1시간) |
| 경보 | 규칙 **3,000개**. 핵심 규칙 300개는 **5초마다**, 나머지는 30초마다 평가 |
| 경보 지연 목표 | 결제 실패율 급증 → 온콜 호출까지 **30초 이내** |
| 경보 누락 | **0건**. 오탐보다 누락이 훨씬 비싸다 |
| 범위 | 교재가 제외한 **사업 지표**(결제 건수·실패율)를 포함한다 |

**설계 포인트**: 교재 설계는 경보가 **질의 서비스 → 시계열 DB**에 기대어 주기적으로 평가한다. 경보 지연 30초와 누락 0이 이 경로를 그대로 써도 되는지 묻는다. 데이터 양은 가장 작지만 경보 요구가 가장 빡빡하다.

**돌발 상황**: "시계열 DB 클러스터가 디스크 장애로 **15분 동안** 질의에 응답하지 못했습니다. 경보 관리자의 질의가 모두 타임아웃 났고, 경보는 하나도 울리지 않았습니다. 그 15분 사이에 PG사 하나가 장애를 일으켜 결제 실패율이 40%까지 올랐지만, 고객 문의가 들어오고서야 알았습니다. 무엇을 바꾸나요?"

## 직접 만들기

다음 항목을 사용자와 함께 채워서 카드를 만든다. 빈 칸은 진행자가 그럴듯한 값을 제안하고 동의를 받는다.

- 무엇을 보나(인프라 지표 / 서비스 지표 / 사업 지표 / IoT 장비) / 출처 종류와 수, 얼마나 자주 바뀌나
- 출처당 지표 수, 레이블 종류(카디널리티를 키우는 레이블이 있나), 수집 주기
- 보관 기간과 단계별 해상도
- 네트워크 환경(단일 데이터 센터 / 여러 리전 / 방화벽 뒤 / 불안정한 회선)
- 경보 규칙 수, 경보 지연 목표, 누락과 오탐 중 무엇이 더 비싼가
- 돌발 상황 1개 (진행자가 만들되, 시나리오의 가장 약한 가정을 깨는 것으로)

## 랜덤

S1~S4 중 하나를 무작위로 고른다. 입문자라면 S1을 권한다.
