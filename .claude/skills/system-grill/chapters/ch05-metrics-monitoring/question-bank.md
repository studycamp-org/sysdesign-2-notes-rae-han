# 질문 은행 (4문항, 20~30분)

**핵심 질문은 정확히 4개다.** 문항이 적은 만큼 질문당 약 5~6분. 묶음 질문은 소항목 최대 2개.
교재의 나머지 주제(데이터 모델, 저장소 종류 선택(범용 DB vs 시계열 DB), 질의 서비스·캐시와 독자 질의어, 이중-델타 인코딩, 시각화, 경보 저장소 스키마)는 질문으로 내지 않는다.
답에 나오면 기록하고, 아키텍처와 핵심 흐름은 마무리 단계에서 진행자가 그린다.

| 단계 | 질문 |
|---|---|
| 요구사항 | Q1 규모 추정 |
| 초안 설계 | **Q2 지표 수집 방식 (풀 vs 푸시) ★** |
| 상세 설계 | Q3 전송 파이프라인과 데이터 줄이기 (묶음) · **Q4 경보 평가와 전달 (묶음, 돌발)** |

각 항목: **질문** / **선택지**(예시, 다른 답도 받음) / **꼬리 질문**(빈약하거나 충돌할 때만, 최대 1회) / **좋은 근거의 신호**(피드백 기준, 답하기 전에는 보여주지 않음).

시나리오별 계산 정답 (진행자 확인용, 하루 ≈ 10⁵초, 포인트 1개 ≈ 16바이트, 압축 전, 사본 제외):

| 시나리오 | 활성 시계열 / 초당 포인트 | 하루 원본 | 보관 기간 전체: 다운샘플링 후 (전) | 따로 볼 숫자 |
|---|---|---|---|---|
| 교재 | 10만 대 × 100 = **10⁷** / ÷ 10초 = **10⁶/s** | 10⁶ × 10⁵ × 16B = **1.6TB** | 7일 11.2 + 23일 ÷6 6.1 + 335일 ÷360 1.5 ≈ **19TB** (365일 원본 **584TB**) | 다운샘플링으로 약 30배 |
| S1 | 2만 × 200 = **4×10⁶** / ÷ 10초 = **4×10⁵/s** | **640GB** | 7일 4.48 + 23일 ÷6 2.45 + 335일 ÷360 0.6 ≈ **7.5TB** (365일 원본 **234TB**) | 돌발: 시계열 × 100 = **4×10⁸** → 색인 메모리가 먼저 터진다 |
| S2 | 5만 × 300 = **1.5×10⁷** / ÷ 15초 = **10⁶/s** | **1.6TB** | 7일 11.2 + 23일 ÷4 9.2 ≈ **20TB** (30일 원본 **48TB**) | 하루에 **새로** 생기는 시계열 50만 × 300 = **1.5×10⁸**(활성의 10배). 30일이면 색인에 약 **4.5×10⁹**개 |
| S3 | 25만 × 100 = **2.5×10⁷** / ÷ 60초 ≈ **4.2×10⁵/s** | **≈ 670GB** | 7일 4.7 + 23일 **÷1** 15.3 + 335일 ÷60 3.7 ≈ **24TB** (365일 원본 **243TB**). 1분 단계를 빼고 7일 뒤 바로 1시간으로 가면 ≈ **8.6TB** | 매장 하나 2시간 버퍼: 5,000 ÷ 60 ≈ 83/s × 16B × 7,200초 ≈ **10MB**. 돌발 800곳 동시 업로드 ≈ **8GB** |
| S4 | 3,000 × 500 = 1.5×10⁶ (÷10초) + 1만 (÷1초) / **1.6×10⁵/s** | **256GB** | 7일 1.8 + 23일 0.93 + 723일 0.49 ≈ **3.2TB** (730일 원본 **187TB**) | 경보 평가 질의: 300 ÷ 5초 + 2,700 ÷ 30초 = **150회/s** |

(포인트 16바이트는 압축 전 값이다. 이중-델타 인코딩 같은 시계열 압축(교재 밖: 고릴라는 포인트당 약 1.4바이트)을 쓰면 다시 10배 가까이 준다. 다운샘플링한 데이터에 평균만 두지 않고 최소·최대·합·개수를 함께 두면 그만큼 곱해진다. Q1·Q3 꼬리 질문에서 쓴다.)

## 요구사항

### Q1. 규모 추정
- **질문**: 활성 시계열 수, 초당 데이터 포인트, 하루 원본 저장량, 보관 기간 전체 저장량(다운샘플링 적용 전과 후)을 직접 계산하세요. 이 시스템에서 가장 먼저 한계에 닿는 것은 무엇인가요? (쓰기 처리량 / 저장 용량 / 시계열 수(색인) / 질의·경보 평가 부하 / 그 밖)
- **좋은 근거의 신호**: 초당 포인트 = 활성 시계열 ÷ 수집 주기. 저장량 = 초당 포인트 × 10⁵ × 포인트 크기 × 일수. 다운샘플링 비율은 `수집 주기 ÷ 새 해상도`라는 것을 알고, 원본 7일이 전체 용량의 대부분을 차지한다는 것을 본다. 지표 모니터링은 **쓰기 부하가 막대하고 읽기는 몰렸다 사라진다**(교재). 시계열 수(카디널리티)는 포인트 수와 별개로 색인 크기를 결정한다는 점(S1 돌발, S2 파드 레이블)을 짚으면 좋다. S3은 60초 주기라 1분 단계가 줄여 주는 게 없다는 것, S4는 데이터는 작지만 경보 질의 부하가 따로 있다는 것을 보면 좋다.
- **꼬리 질문**: "수집 주기를 10초에서 1초로 줄이면 무엇이 10배가 되고, 무엇은 그대로인가요?" / "레이블 하나에 값이 1만 가지인 것을 추가하면 초당 포인트와 시계열 수는 각각 어떻게 되나요?"

**▶ 요구사항 체크포인트**

## 초안 설계

### Q2. 지표 수집 방식 (풀 vs 푸시) ★핵심
- **질문**: 지표를 어떻게 모으나요? 수집기는 누구에게서 무엇을 받고, 수집기가 여러 대일 때 일은 어떻게 나누나요?
- **선택지**: A) 풀 — 수집기가 서비스 탐색으로 대상 목록을 받아 각 출처의 `/metrics` 엔드포인트를 주기적으로 긁어 간다(그림 5.8) B) 푸시 — 출처 서버의 수집 에이전트가 모아서(필요하면 집계해서) 로드밸런서 뒤 수집기 클러스터로 보낸다(그림 5.13) C) 혼합 — 기본은 풀, 짧은 작업·방화벽 밖은 푸시(푸시 게이트웨이 등) D) 그 밖(관리형 서비스, 엣지마다 로컬 수집기를 두고 본사로 푸시 등). 함께 정할 것: 수집기 여러 대에 출처를 나누는 방법, 전송 프로토콜(TCP/UDP), 출처 인증
- **좋은 근거의 신호**: 표 5.3의 여섯 축 — 디버깅(풀: `/metrics`를 언제든 볼 수 있다), **상태 진단**(풀: 응답이 없으면 바로 장애 / 푸시: 안 오면 네트워크 문제인지 서버 문제인지 모른다), **생존 기간이 짧은 프로세스**(푸시가 낫다. 풀은 긁어 가기 전에 끝난다 → 푸시 게이트웨이), **방화벽 등 네트워크**(푸시가 낫다. 풀은 모든 엔드포인트가 수집기에서 접근 가능해야 한다), 성능(푸시는 보통 UDP로 지연이 낮다는 주장과 TCP 오버헤드가 작다는 반론), **데이터 신빙성**(풀은 대상 목록이 정해져 있다 / 푸시는 아무나 보낼 수 있다 → 허용 목록·인증) — 중 시나리오에 맞는 축을 골라 근거로 쓴다. 정답은 없고 **장단점을 비교하는 능력**이 중요하다(교재). 시나리오 연결: S2 짧은 배치 작업과 잦은 출처 변화, S3 방화벽·아웃바운드만, S4 상태 진단과 누락 0.
- **세부 질문** (고른 방식에 맞는 것 **하나만**, 같은 질문 안에서):
  - **풀**: "수집기 수십 대가 같은 서버를 중복해서 긁지 않게 어떻게 나누나요? 수집기 한 대가 죽으면 그 몫은요?"
    - 신호: 서비스 탐색(etcd·주키퍼, 쿠버네티스 API)에서 대상 목록과 변경 알림을 받고, **안정 해시 링**으로 구간마다 담당 수집기를 정한다(그림 5.11). 수집기가 빠지면 그 구간만 다음 수집기로 넘어간다. 대상이 아주 자주 바뀌면(S2) 목록 갱신 주기와 재배치 비용을 짚는다.
  - **푸시**: "수집기 클러스터가 몰리거나 일부가 죽으면 에이전트의 데이터는요? 지표가 안 들어오는 서버가 죽은 건지 어떻게 아나요?"
    - 신호: 로드밸런서 + 수집기 자동 규모 확장(그림 5.13), 에이전트 로컬 버퍼에 잠시 보관 후 재전송. 단, 오토스케일로 출처 서버 자체가 사라지면 버퍼째 잃는다(교재). 상태 진단은 별도 박동(heartbeat)·마지막 수신 시각 추적이 필요하다.
  - **혼합**: "어떤 지표가 풀로, 어떤 지표가 푸시로 가나요? 경보 규칙을 짤 때 두 경로의 차이를 신경 써야 하나요?"
    - 신호: 오래 사는 서비스는 풀, 짧은 작업은 푸시 게이트웨이. 푸시 게이트웨이에 남은 마지막 값이 계속 '살아 있는 것처럼' 보이는 문제, 게이트웨이 자체가 단일 장애 지점이 되는 문제(교재 밖).
  - **그 밖**: "그 방식에서 상태 진단(출처가 죽었는지)과 데이터 신빙성(아무나 못 보내게)은 어떻게 챙기나요?"
- **꼬리 질문**:
  - 공통: "수집 대상이 지금의 10배가 되면 그 방식에서 가장 먼저 무엇이 문제가 되나요?"
  - 풀: "데이터 센터(리전)가 여러 개면 수집기는 어디에 두나요?"
  - 푸시: "UDP로 보내다 일부가 유실되면 그걸 누가 알 수 있나요? 이 시나리오에서 그 유실은 괜찮나요?"

**▶ 초안 설계 체크포인트**

## 상세 설계

### Q3. 전송 파이프라인과 데이터 줄이기 (묶음)
- **질문**:
  1. 수집기와 시계열 DB 사이에 무엇을 두나요? A) 수집기가 시계열 DB에 바로 기록 B) 카프카 같은 큐를 두고 소비자가 DB에 기록(그림 5.22) C) 큐 없이 수집기 로컬 버퍼·WAL로 버팀 D) 큐 없이 대규모 처리가 가능한 시계열 DB(교재: 고릴라) E) 그 밖. 큐를 둔다면 파티션 기준은?(지표 이름 / 레이블 / 우선순위)
  2. 데이터를 어디서, 언제 줄이나요? 집계 지점 A) 수집 에이전트 B) 파이프라인의 스트림 처리 엔진(플링크 등, 집계 결과만 저장) C) 질의 시점(원본 저장) D) 지표마다 다르게 — 그리고 보관 기간 동안의 다운샘플링 단계(언제, 어떤 해상도로, 평균만 / 최소·최대·합·개수도)와 오래된 데이터의 냉동 저장소
- **좋은 근거의 신호**: 큐는 **시계열 DB 장애 시 데이터 소실을 막고**, 수집과 처리의 결합도를 낮추며, 파티션으로 확장한다(지표 이름으로 나누면 소비자가 이름별로 집계 가능, 중요 지표 우선 처리). 대신 운영할 시스템이 하나 늘고 지연이 조금 는다. 지표는 "때로 소실돼도 아주 심각하지 않다"(교재)는 점이 큐를 생략할 근거가 되기도 한다. 집계: 에이전트 집계는 보내는 양을 줄이지만 할 수 있는 게 적다. **스트림 집계는 저장량을 크게 줄이지만 늦게 도착한 데이터 처리가 어렵고 원본이 없어 정밀도·유연성을 잃는다.** 질의 시점 집계는 유연하지만 느리다. 다운샘플링은 오래된 데이터의 해상도를 낮춰 용량을 수십 배 줄이지만 **원래 값(급등·급락)이 사라진다** → 평균만 두면 짧은 스파이크를 놓친다. 질의의 **85%가 최근 26시간** 데이터(교재)라 원본은 짧게 두고 빨리 읽히게, 오래된 것은 싸게(냉동 저장소, 대신 질의가 느림) 둔다는 연결을 보면 좋다. 시나리오 연결: S1 카디널리티(줄여야 할 것은 포인트가 아니라 시계열 수), S2 파드 단위 원본을 서비스 단위로 미리 합칠지 + 30일 보관, S3 늦게 도착하는 데이터(스트림 집계와 충돌) + 60초 주기라 1분 단계 무의미, S4 1초 지표의 정밀도와 2년 감사 보관.
- **꼬리 질문**: "시계열 DB가 1시간 동안 죽으면 그 1시간 치 데이터는 어디에 얼마나 쌓이나요?" / "스트림에서 1분 단위로 집계했는데 5분 늦게 도착한 포인트는 어떻게 하나요?" / "1년 전 이맘때와 오늘의 CPU 최고치를 비교하고 싶다면, 당신의 다운샘플링 정책에서 가능한가요?"

### Q4. 경보 평가와 전달 (묶음, 돌발 상황 포함)
- **질문**: 먼저 시나리오 카드의 **돌발 상황**을 제시하고, 그 상황을 전제로 답하게 한다.
  1. 경보 규칙은 어디서, 어떻게 평가하나요? A) 경보 관리자가 정해진 주기마다 질의 서비스를 호출해 임계값과 비교(교재, 그림 5.19) B) 수집 파이프라인에서 스트림으로 들어오는 대로 평가 C) 에이전트·엣지에서 로컬로 평가 D) 섞어서(핵심 규칙만 다른 경로) E) 그 밖. '데이터 없음'은 어떻게 다루나요?
  2. 경보가 쏟아지거나 겹칠 때 어떻게 줄이고, 알림은 어떻게 확실히 전달하나요? (병합·중복 제거·그룹화·억제, 경보 상태 저장소, 카프카 + 경보 소비자 + 재시도, 모니터링 시스템 자신의 감시 등)
  - 돌발 상황 때문에 앞의 결정 중 바꿀 것이 있나요?
- **좋은 근거의 신호**: 교재 흐름은 규칙 설정 파일(YAML) → 캐시 → 경보 관리자가 주기적으로 질의 → 임계값 위반 시 경보 이벤트 → **경보 저장소**(카산드라 같은 키-값 저장소에 활성화·응답 대기·발령·해결 상태) → **카프카** → 경보 소비자 → 이메일·문자·페이저듀티·웹훅. 경보 관리자는 **필터링·병합·중복 제거**(같은 인스턴스에서 짧은 시간 안에 생긴 경보는 하나로), 접근 제어, 재시도를 맡는다. 질의 기반 평가는 단순하고 저장된 데이터 전체를 쓸 수 있지만 **시계열 DB에 의존**하므로 DB 장애 = 경보 침묵(S4 돌발)이 된다 → 핵심 규칙은 스트림으로 따로 평가하거나, 경보 경로를 감시하는 **데드맨 스위치**(항상 울려야 하는 경보가 안 오면 외부에서 호출, 교재 밖)를 둔다. 스트림 평가는 빠르지만 긴 구간 비교가 어렵다. 경보 폭풍(S2)에는 서비스 단위 그룹화와 상위 원인 경보가 하위 경보를 억제하는 방법, 회선 끊김(S3)에는 '데이터 없음'과 '실제 이상'을 구분하고 늦게 온 데이터로 이미 지난 경보를 다시 울리지 않는 방법, 카디널리티 폭발(S1)에는 레이블 허용 목록·시계열 수 상한으로 출처를 막는 방법을 본다. 카프카를 쓰면 알림이 최소 1회 전달되므로 같은 알림 중복은 경보 ID로 막는다.
