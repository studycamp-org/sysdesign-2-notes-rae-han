## 1. 요구사항 (교재 기준안)

- 용도: **인프라 운영 지표**(에러 모니터링·액세스 모니터링이 아님). 사용 범위: **내부용**(SaaS 아님).
- 지표: CPU 부하, 메모리 사용률, 디스크 사용량 등 운영 지표. **사업 지표는 제외**.
- 규모: 일간 능동 사용자 1억 명, 서버 풀 1,000개 × 풀당 서버 100대 = **서버 10만 대**. (보충) 서버당 지표 약 100개 → **약 1,000만 개 지표**.
- 보관: 최대 **1년**. 7일 원본 → 7일 뒤 **1분 단위로 30일** → 그 뒤 **1시간 단위**.
- 알림: 이메일, 전화, 페이저듀티, 웹훅 등.
- 비기능: 규모 확장성, 낮은 응답 지연(대시보드·경보 질의), 안정성(중요 경보를 놓치지 않음), 유연성(새 기술 통합).
- 제외: 로그 모니터링(ELK 등), 분산 시스템 추적.
- (보충) 교재 기준 계산: 10⁷ 시계열 ÷ 10초 = 초당 10⁶ 포인트, 포인트 16바이트면 하루 약 1.6TB(압축 전).

## 2. 개략적 설계

- **다섯 컴포넌트**: 데이터 수집 / 데이터 전송 / 데이터 저장소 / 경보 / 시각화.
- **데이터 모델**: 시계열 = 지표 이름 + 레이블 집합(예: `host:i631,env:prod`) + `<타임스탬프, 값>` 배열. 같은 이름이라도 레이블 조합마다 다른 시계열. (보충) 레이블 값의 종류가 많을수록 시계열 수(카디널리티)가 곱으로 늘어난다.
- **데이터 접근 패턴**: 쓰기 부하가 막대하다(초당 수백만 포인트, 끊임없이). 읽기는 일시적으로 치솟았다 사라진다(대시보드를 열 때, 장애 때). 시각화와 경보 서비스가 읽기를 일으킨다.
- **저장소 선택**: 범용 DB도 이론상 시계열을 처리할 수 있지만, 이 규모에 맞추려면 전문가 수준의 튜닝이 필요하고 시계열 연산(이동 평균 등)을 SQL로 쓰기 어렵다. NoSQL(카산드라·빅테이블)도 가능하지만 확장 가능한 스키마 설계에 깊은 지식이 필요하다. → **시계열 DB**(OpenTSDB, InfluxDB, 프로메테우스 등)를 쓴다. 대량 쓰기와 빠른 실시간 분석, 레이블 기반 색인을 지원한다.
- **개략적 설계안**(그림 5.7): 지표 출처 → 지표 수집 → 시계열 DB ← 질의 시스템 ← 경보 시스템 / 시각화 시스템. 경보 시스템 → 이메일·단문 메시지·페이저듀티·HTTPS 엔드포인트.

## 3. 상세 설계

### 지표 수집: 풀 vs 푸시
- 카운터·CPU 같은 지표는 **때로 소실돼도 아주 심각하지 않다** → 보내는 쪽이 전송 성공을 신경 쓰지 않아도 된다.
- **풀**(그림 5.8): 수집기가 실행 중인 애플리케이션에서 주기적으로 가져온다. 대상 목록이 필요하다 → 파일에 DNS/IP를 두면 단순하지만 서버가 수시로 바뀌면 안 된다 → **서비스 탐색**(etcd, 주키퍼). 각 서비스가 SDS에 자기 가용성 정보를 등록하고, 수집기는 SDS에서 엔드포인트 목록을 받아 미리 정한 HTTP 엔드포인트(`/metrics`)에서 가져간다. 목록 변경 알림 콜백을 등록하거나 주기적으로 다시 가져온다.
  - 수집기 **서버 풀**이 필요하고, 같은 서버를 중복 수집하지 않도록 **안정 해시 링**으로 구간마다 담당 수집기를 정한다(그림 5.11).
- **푸시**(그림 5.12): 출처 서버에 **수집 에이전트**를 설치해 서비스가 만든 지표를 모아 주기적으로 수집기에 보낸다. 에이전트가 먼저 **집계**하면 보내는 양이 줄고, 수집기가 거부하면 작은 버퍼에 잠시 보관했다 재전송한다. 하지만 출처 클러스터가 **자동 규모 확장**되면 서버가 사라지면서 버퍼 데이터가 사라질 수 있다 → 수집기 클러스터도 자동 규모 확장하고 앞에 **로드밸런서**를 둔다(그림 5.13).
- **표 5.3 풀 vs 푸시**:

| 항목 | 풀 | 푸시 |
|---|---|---|
| 손쉬운 디버깅 | `/metrics`로 언제든 확인. **풀이 낫다** | |
| 상태 진단 | 응답이 없으면 바로 장애. **풀이 쉽다** | 안 오면 네트워크 탓인지 서버 탓인지 모름 |
| 생존 기간이 짧은 프로세스 | 긁어 가기 전에 끝날 수 있음(푸시 게이트웨이로 보완) | **푸시가 낫다** |
| 방화벽 등 복잡한 네트워크 | 모든 `/metrics`가 접근 가능해야 함. 데이터 센터가 여럿이면 문제 | 로드밸런서 + 자동 확장 수집기면 어디서든. **푸시가 낫다** |
| 성능 | 보통 TCP | 보통 UDP → 지연 낮음 (반론: TCP 오버헤드는 지표 양에 비해 작다) |
| 데이터 신빙성 | 대상 목록이 정해져 있어 믿을 수 있음 | 아무나 보낼 수 있음 → 허용 목록·인증 |

- 대표 사례: 풀 = 프로메테우스 / 푸시 = 아마존 클라우드워치, 그래파이트. **정답은 없고 장단점 비교 능력이 중요하다.**

### 지표 전송 파이프라인의 규모 확장
- 수집기 클러스터는 자동 규모 확장되어야 한다. 하지만 **시계열 DB에 장애가 나면 데이터가 손실**될 수 있다 → 수집기 → **카프카** → 소비자(스트림 처리) → 시계열 DB.
  - 카프카: 안정적·확장성 높은 분산 메시지 플랫폼. 수집과 처리의 결합도를 낮추고, DB 장애에도 데이터가 소실되지 않는다.
  - 카프카 파티션으로 확장: 대역폭에 맞춰 파티션 수 설정 / **지표 이름**으로 파티션을 정하면 소비자가 이름별로 집계 가능 / 레이블로 더 세분화 / 중요 지표 **우선순위**.
  - 카프카의 대안: 큐 없이도 대규모 처리가 가능한 시스템 — 페이스북 **고릴라**(인메모리 시계열 DB). (보충) 카프카를 운영하는 비용이 만만치 않아 생략하는 경우도 있다.

### 데이터 집계 지점
- **수집 에이전트**: 카운터를 분 단위로 집계하는 정도의 단순한 것.
- **데이터 수집 파이프라인**: 저장 전에 집계하려면 **플링크** 같은 스트림 처리 엔진이 필요. DB에는 계산 결과만 기록 → 기록량이 크게 준다. 하지만 **늦게 도착하는 데이터 처리가 어렵고**, 원본을 보관하지 않아 **정밀도·유연성**을 잃는다.
- **질의 시점**: 원본을 그대로 보관하고 질의할 때 필요한 구간으로 집계. 유연하지만 전체 데이터를 대상으로 계산해 **느리다**.

### 질의 서비스
- 질의 서버 클러스터. 시각화·경보의 요청을 시계열 DB로 처리. 클라이언트와 시계열 DB의 **결합도를 낮춘다**.
- **캐시 계층**: 질의 결과를 캐시해 DB 부하를 낮추고 성능을 높인다.
- 질의 서비스가 곤란한 경우: 상용 시각화·경보 시스템은 널리 쓰이는 시계열 DB와 바로 붙는 플러그인이 강력해 질의 서비스·캐시가 필요 없을 수 있다.
- **질의어**: 프로메테우스·InfluxDB는 SQL이 아닌 독자 질의어. 이동 평균 같은 시계열 연산은 SQL로 쓰면 매우 복잡하고, Flux로는 몇 줄이면 된다.

### 저장소 계층
- 시계열 DB는 신중하게 고른다. 페이스북 연구에 따르면 **질의의 85%가 최근 26시간** 데이터 → 이를 활용하는 DB가 성능상 크게 유리.
- **데이터 인코딩 및 압축**: **이중-델타 인코딩** — 타임스탬프는 대개 10초 간격이라 기준값과 차이만 저장(1610087371, 10, 10, 9, 11). 타임스탬프 하나는 32비트지만 10은 4비트로 충분. (보충) 엄밀한 delta-of-delta는 델타끼리의 차이(0, -1, 2)를 한 번 더 저장한다.
- **다운샘플링**: 오래된 데이터의 해상도를 낮춘다. 7일 이내 원본 / 30일 이내 1분 / 1년 이내 1시간. 예: 10초 해상도 6개 → 30초 해상도 2개(표 5.4 → 5.5, 평균). (보충) 평균만 남기면 짧은 급등이 사라진다 → 최소·최대·합·개수를 함께 두는 경우가 많다.
- **냉동 저장소**: 잘 쓰지 않는 비활성 데이터를 싼 저장소에 둔다.

### 경보 시스템 (그림 5.19)
1. 규칙 설정 파일(디스크, **YAML**)을 가져와 **캐시**에 보관.
2. **경보 관리자**가 캐시에서 경보 설정을 가져온다.
3. 정해진 주기마다 **질의 서비스**를 호출해 임계값을 위반하면 경보 이벤트 생성. 그 외: 경보 **필터링·병합·중복 제거**(짧은 시간 같은 인스턴스의 경보는 하나로), **접근 제어**(권한 있는 사람만 경보 관리), **재시도**(알림이 최소 한 번은 전달되도록).
4. **경보 저장소**: 카산드라 같은 키-값 저장소. 모든 경보의 상태(활성화·응답 대기·경보 발령·문제 해결)를 보관.
5. 경보 이벤트를 **카프카**에 전달.
6. **경보 소비자**가 카프카에서 읽는다.
7. 이메일·단문 메시지·페이저듀티·HTTPS 엔드포인트로 알림.
- (보충) 경보 시스템을 직접 만들기보다 상용·오픈소스(Alertmanager 등)를 쓰는 경우가 많다.

### 시각화
- 데이터 계층 위에 만든다. 지표 대시보드(다양한 시간 범위), 경보 대시보드(경보와 상태). 직접 만들기 어려우므로 **그라파나** 같은 상용·오픈소스를 쓰는 것이 낫다.

### 최종 설계안 (그림 5.22)
- 지표 출처 → 지표 수집기 → **카프카** → 소비자 → 시계열 DB ← 질의 서비스(+ **캐시**) ← 경보 시스템 / 시각화 시스템. 경보 → 이메일·문자·페이저듀티·HTTPS.
- 그림 5.7 대비 추가: 카프카 + 소비자(DB 장애 시 소실 방지, 확장), 질의 서비스 앞 캐시.

## 시나리오별로 교재 기준안이 흔들리는 지점

| 시나리오 | 교재 가정이 깨지는 곳 | 검토할 만한 대안 |
|---|---|---|
| S1 사내서버 | 레이블을 팀이 자유롭게 붙임 → 카디널리티 폭발 | 교재 그대로(풀 + 안정 해시, 전용 TSDB, 교재 다운샘플링)가 충분. 큐는 선택. 돌발은 **출처에서 막는다**: 레이블 허용 목록·시계열 수 상한(초과 시 수집 거부), `user_id` 같은 고유 값은 지표 대신 로그·추적으로. 핵심 경보 규칙은 미리 계산(기록 규칙)해 평가 부하를 낮춘다 |
| S2 컨테이너 | 출처가 수시로 바뀜, 20초짜리 작업, 파드 이름 레이블로 새 시계열 폭증 | 쿠버네티스 API를 서비스 탐색으로 쓰는 풀 + 짧은 작업만 푸시 게이트웨이(혼합), 또는 노드마다 에이전트(데몬셋)로 푸시. 수집 단계에서 파드 단위를 서비스 단위로 미리 합쳐 시계열 수 축소. 돌발은 수집기 샤드 자동 확장 + **서비스 단위 그룹화**, 상위 경보(서비스 장애)가 하위(파드별 CPU) 억제, '데이터 없음'은 수집 실패와 구분 |
| S3 엣지매장 | 밖에서 매장 접근 불가, 회선이 끊겼다 이어짐, 60초 주기 | **푸시**(매장 게이트웨이 에이전트 → 본사 로드밸런서, 인증 필수) + 매장 로컬 버퍼(2시간 ≈ 10MB). 늦은 데이터 때문에 스트림 집계보다 **질의 시점 집계**나 지연 허용 창. 1분 다운샘플링 단계는 생략. 온도 경보는 **매장 로컬 평가**도 검토. 돌발은 '매장 연결 끊김' 경보 하나로 묶어 장비 경보 억제, 늦게 온 데이터는 저장만 하고 과거 시점 경보는 재발령하지 않음 |
| S4 결제SLO | 사업 지표 포함, 1초 지표, 경보 30초·누락 0, 2년 보관 | 핵심 지표는 **스트림에서 바로 평가**(DB를 거치지 않는 경로)하고 나머지는 교재처럼 질의 기반. 경보 경로를 감시하는 **데드맨 스위치**(외부 서비스가 박동이 끊기면 호출). 시계열 DB 복제·이중화. 2년 보관은 1시간 해상도 + 냉동 저장소, 단 최대·최소도 함께 보관. 돌발은 "DB 장애 = 경보 침묵"을 끊는 것이 핵심 |
