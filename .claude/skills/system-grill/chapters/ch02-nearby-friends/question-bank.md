# 질문 은행 (7문항, 20~30분)

**핵심 질문은 정확히 7개다.** 질문당 약 3분. 묶음 질문은 소항목 최대 2개.
교재의 나머지 주제(친구 관계 저장, 친구 추가·삭제 콜백, 친구가 아주 많은 사용자, 재접속 폭주, 펍/섭 대안 기술, 최종 흐름 서술)는 질문으로 내지 않는다.
답에 나오면 기록하고, 아키텍처와 핵심 흐름은 마무리 단계에서 진행자가 그린다. 단, S3·S4는 거대 채널·밀집 격자가 돌발 상황이므로 Q6에서 다룬다.

| 단계 | 질문 |
|---|---|
| 요구사항 | Q1 규모 추정 · Q2 갱신 주기와 활성 판단 (묶음) |
| 초안 설계 | Q3 통신 방식과 서버 구조 (묶음) · **Q4 위치 변경 전파 방식 ★** · Q5 위치 저장소 (묶음) |
| 규모 확장 | **Q6 펍/섭 클러스터 확장 (돌발)** · Q7 웹소켓 서버와 위치 캐시 확장 (묶음) |

각 항목: **질문** / **선택지**(예시, 다른 답도 받음) / **꼬리 질문**(빈약하거나 충돌할 때만, 최대 1회) / **좋은 근거의 신호**(피드백 기준, 답하기 전에는 보여주지 않음).

시나리오별 계산 정답 (진행자 확인용):

| 시나리오 | 동시 접속 | 위치 갱신 QPS | 초당 전파 메시지 (팬아웃) | 펍/섭 서버 수 감 (CPU, 서버당 10만 push/s) |
|---|---|---|---|---|
| S1 | 2,000만 × 10% = 200만 | 200만 / 30 ≈ **6.7만** | 6.7만 × 150 × 10% ≈ **100만** | ≈ 10대 |
| S2 | 1억 × 10% = 1,000만 | 1,000만 / 30 ≈ **33.4만** | 33.4만 × 400 × 10% ≈ **1,400만** | ≈ 140대 |
| S3 | 피크 200만 × 20% = 40만 | 40만 / 5 = **8만** (평소 2만) | 8만 × 19(크루원) ≈ **150만** | ≈ 15대. 이력 쓰기도 8만/s |
| S4 | 500만 × 10% = 50만 | 50만 / 30 ≈ **1.7만** | 1.7만 × 9N (칸당 평균 N명, 내 칸 + 인접 8칸) | 밀도에 따라 다름. 식을 세웠는지를 본다 |

(교재 S2 메모리: 1억 × 구독 친구 100명 × 포인터 20B ≈ 200GB → 100GB 서버 2대. **CPU가 병목**이라는 결론이 핵심.)

## 요구사항

### Q1. 규모 추정
- **질문**: 동시 접속자, 위치 갱신 QPS, 초당 친구에게 전달할 메시지 수를 직접 계산하세요. 읽기 위주인가요, 쓰기 위주인가요?
- **좋은 근거의 신호**: 동시 접속 = DAU × 비율, 갱신 QPS = 동시 접속 / 주기, 팬아웃 = 갱신 QPS × 친구 수 × 반경 안 활성 비율. 팬아웃이 갱신 QPS보다 **한두 자릿수 크다**. 쓰기와 푸시가 압도적이라 1장의 "읽기 사본 + 캐시" 공식이 통하지 않는다.
- **꼬리 질문**: "위치 갱신 QPS와 친구에게 보내는 메시지 수 중 어느 쪽이 먼저 병목이 될까요?"

### Q2. 갱신 주기와 활성 판단 (묶음)
- **질문**:
  1. 위치를 얼마나 자주 보내고, 유실·지연을 얼마나 허용하나요? A) 고정 30초 B) 더 짧은 고정 주기 C) 이동 속도·배터리에 따른 적응형 D) 앱 화면이 열려 있을 때만
  2. 친구가 "활성"인지는 어떻게 판단하나요? A) 웹소켓 연결 여부 B) 마지막 갱신 후 일정 시간(TTL) C) 앱이 상태를 명시적으로 보냄 D) 조합
- **좋은 근거의 신호**: 주기는 이동 속도와 반경에서 출발한다(걷는 속도 시속 3~4마일이면 30초에 약 50m). 주기를 반으로 줄이면 QPS와 팬아웃이 2배. 유실 허용이면 최대 한 번 전달(at-most-once) 버스를 쓸 수 있다. 마지막 갱신 시각을 함께 보여준다. 연결은 끊김이 잦은 모바일에서 불안정한 신호이고, TTL은 갱신마다 연장되며 끊기면 저절로 만료된다.
- **꼬리 질문**: "주기를 5초로 줄이면 Q1 숫자는 어떻게 되나요?" / "친구가 지하철 터널에서 2분 끊겼다 돌아오면 화면에서 사라졌다 나타나나요?"

## 초안 설계

### Q3. 통신 방식과 서버 구조 (묶음)
- **질문**:
  1. 단말과 서버는 어떻게 통신하나요? A) P2P B) 짧은 주기 폴링 C) 롱 폴링 D) SSE E) 웹소켓 F) MQTT
  2. 친구 추가·삭제 같은 부가 기능과 실시간 위치 처리를 A) 한 서버 군에 B) 무상태 API 서버와 유상태 실시간 서버로 나눠서. 그리고 앱이 위치를 보내는 시점은 언제인가요?
- **좋은 근거의 신호**: P2P는 모바일 연결 불안정과 전력 부족 때문에 어렵다. 폴링은 바뀐 게 없어도 요청이 생기고 주기만큼 지연된다. 웹소켓은 양방향·저지연이지만 서버가 **유상태**가 된다. 무상태 API 서버는 자동 확장이 쉬우니 분리 근거가 있다. 위치는 단말만 알기 때문에 **접속 시 1번(초기화, 반경 안 친구 목록 응답) + 주기적으로** 두 번 보낸다.
- **꼬리 질문**: "웹소켓 서버가 유상태라는 게 배포나 축소할 때 어떤 문제를 만드나요?" / "초기화 메시지 없이 주기 갱신만 있으면 접속 직후 화면은 어떻게 되나요?"

### Q4. 위치 변경 전파 방식 ★핵심
- **질문**: 사용자 A의 위치가 바뀌었을 때, A의 친구들과 연결된 웹소켓 서버들에 어떻게 전달할까요?
- **선택지**: A) 사용자별 채널을 둔 경량 펍/섭(레디스 펍/섭 등) B) 친구 목록을 조회해 친구가 붙은 서버로 직접 전송 C) 영속 메시지 큐(Kafka 등) D) 액터 런타임(Erlang/Elixir) E) 공간(지오해시) 단위 채널 F) 조합
- **좋은 근거의 신호**: 교재는 사용자마다 전용 채널을 두고 친구들의 연결 핸들러가 구독한다. 레디스 펍/섭은 채널이 매우 싸고 메시지를 저장하지 않는다(유실 허용과 맞음). 거리 필터는 내 위치를 아는 구독 측 핸들러가 한다. Q2 유실 정책과 연결한다.
- **세부 질문** (고른 방식에 맞는 것 **하나만**, 같은 질문 안에서):
  - **사용자별 펍/섭 채널**: "접속할 때 친구 중 누구의 채널을 구독하나요(전원 / 활성 친구만 / 반경 안 친구만)? 거리 필터는 발행 측과 구독 측 중 어디서 하나요?"
    - 신호: 교재는 **활성·비활성 상관없이 친구 전원**을 구독한다. 비활성 채널은 메시지가 없어 메모리만 조금 쓰고 CPU는 안 쓴다. 활성 친구만 구독하면 친구가 활성으로 바뀔 때 새로 구독하는 로직이 필요하다.
  - **직접 전송**: "친구가 지금 어느 웹소켓 서버에 붙어 있는지 어떻게 아나요? 그 정보는 얼마나 자주 바뀌나요?"
    - 신호: 연결 레지스트리 조회가 갱신마다 친구 수만큼 생긴다. 재접속마다 바뀐다. 결국 펍/섭이 해주는 일을 직접 만드는 셈이다.
  - **영속 메시지 큐**: "사용자 수만큼 토픽이나 파티션을 둘 수 있나요? 저장 비용은 Q2 유실 정책과 맞나요?"
    - 신호: 토픽·파티션 수백만 개는 메타데이터 부담이 크다. 영속성은 이 요구사항에서 낭비일 수 있다. 위치 이력 파이프라인으로는 잘 맞는다.
  - **액터 런타임**: "사용자당 프로세스가 수천만 개면 노드 간 분산과 장애 시 이동은요? 팀 역량은요?"
    - 신호: BEAM 프로세스는 매우 가볍고 분산 구독이 내장돼 있다(교재도 대안으로 언급). 운영 인력을 구하기 어렵다.
  - **공간 단위 채널**: "격자 크기는 얼마로 하고, 격자 경계 사용자는 어떻게 처리하나요?"
    - 신호: 내 칸 채널에 발행, 내 칸 + 인접 8칸 구독. 밀집 지역은 칸 하나에 구독자가 몰린다. 임의 사용자 노출(S4)에 맞는 방식.
  - **그 밖의 기술**: "이 팬아웃 규모와 유실 정책에서 이 기술의 한계와 대응책은?"
- **꼬리 질문**:
  - 사용자별 채널: "친구 5,000명인 사용자의 채널은 얼마나 무거운가요?"
  - 직접 전송: "Q1 팬아웃 수만큼 레지스트리를 조회하면 그 저장소는 버티나요?"
  - 영속 큐: "아무도 다시 읽지 않는 위치 메시지를 디스크에 쓰는 비용은 정당한가요?"
  - 공간 채널: "이 방식으로 '친구만' 보여주려면 무엇이 더 필요한가요?"

### Q5. 위치 저장소 (묶음)
- **질문**:
  1. 사용자별 **최신 위치**는 어디에, 어떤 키·값과 만료 정책으로 두나요? A) 인메모리 키-값(레디스) + TTL B) RDB C) 웹소켓 서버 메모리에만 D) 저장 안 함
  2. **위치 이력**을 저장하나요? A) 저장 안 함 B) RDB C) 쓰기에 강한 분산 DB(Cassandra 등) D) 메시지 큐 → 배치로 데이터 레이크
- **좋은 근거의 신호**: 최신 위치는 키 `user_id` → 값 `{위도, 경도, 시각}`. 최신 값 하나만 필요하고 영속성이 중요하지 않으니 레디스가 맞고, TTL을 활성 판단(Q2)과 겸한다. 이력은 쓰기가 압도적이고 수평 확장이 필요해 Cassandra가 교재 기준안이며 사용자 ID로 샤딩한다. 시나리오의 데이터 보호 정책(보관 기간, 저장 금지)과 맞춘다.
- **꼬리 질문**: "레디스가 재시작되어 최신 위치가 전부 사라지면 무슨 일이 생기나요?" / "초당 수십만 건 이력을 RDB 한 대에 쓰면요?"

## 규모 확장

### Q6. 펍/섭 클러스터 확장 (돌발 상황 포함)
- **질문**: 먼저 시나리오 카드의 **돌발 상황**을 제시하고, 그 상황을 전제로 답하게 한다.
  - 펍/섭 서버가 몇 대 필요한지 메모리와 CPU로 각각 계산하고, 채널을 서버들에 어떻게 나누나요? A) 사용자 ID 모듈러 해시 B) 안정 해시(해시 링) + 서비스 탐색(etcd, ZooKeeper) C) 레디스 클러스터에 맡김 D) 지역별 클러스터
  - 돌발 상황 때문에 앞의 결정 중 바꿀 것이 있나요?
- **좋은 근거의 신호**: 메모리(구독 관계 × 20B)보다 CPU(초당 push / 서버당 처리량)가 병목. 서비스 탐색에 해시 링을 두고 웹소켓 서버가 사본을 든다. 펍/섭 서버는 구독자 상태를 들고 있어 **유상태** → 서버를 늘리면 많은 채널이 옮겨 가고 재구독이 몰려 갱신이 유실될 수 있다. 그래서 오버 프로비저닝 + 부하가 가장 낮은 시간에 증설. 장애 시 대기 노드로 교체하고 그 노드의 채널만 재구독. 지역 데이터 거주(S2), 거대 채널(S3), 밀집 격자(S4)는 따로 본다.
- **꼬리 질문**: "모듈러 해시로 1대를 추가하면 채널 몇 퍼센트가 이동하나요? 해시 링이면요?" / "구독자 3만 명인 채널에 한 번 발행하면 서버가 몇 번 push 하나요?"

### Q7. 웹소켓 서버와 위치 캐시 확장 (묶음)
- **질문**:
  1. 웹소켓 서버를 줄이거나 새 버전을 배포할 때 기존 연결은 어떻게 처리하나요?
  2. 위치 캐시는 한 대로 충분한가요? 크기와 쓰기 QPS로 판단하고, 나눈다면 기준과 복제 방식은?
- **좋은 근거의 신호**: 유상태라 그냥 내리면 연결이 끊긴다 → 로드밸런서에서 **draining**으로 표시해 새 연결을 막고 기존 연결이 끊긴 뒤 내린다. 위치 캐시는 1,000만 × 약 100B ≈ 1GB라 메모리는 충분하지만 초당 수십만 쓰기는 한 대에 무겁다 → 사용자 ID 샤딩 + 샤드별 대기 복제본. 서버 여러 대가 한꺼번에 재시작되면 재접속 폭주가 초기화 경로(친구 목록, 위치 일괄 조회, 전원 재구독)를 때린다 → 백오프 + 지터, 점진 재시작.
- **꼬리 질문**: "draining 중인 서버의 연결이 몇 시간째 안 끊기면요?" / "웹소켓 서버 10대가 동시에 재시작되면 무엇이 먼저 무너지나요?"
