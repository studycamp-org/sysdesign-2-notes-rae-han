# 학습 내용 요약 (진행자 참고용)

출처: 「가상 면접 사례로 배우는 대규모 시스템 설계 기초 2」 2장 주변 친구, 스터디 정리본 `02_주변친구.md`.
정리본에서 비어 있던 섹션(클라이언트 초기화, 사용자 DB, 위치 정보 캐시, 펍/섭 서버 메모리·CPU)은 교재 내용으로 보충했고 `(보충)`으로 표시했다.
`힌트` 응답, 피드백, 결과 문서의 "교재와 다르게 간 곳" 섹션에 쓴다. 답하기 전에 기준안을 먼저 말하지 않는다.

## 용어와 교재 밖 기술

- 용어(교재 표기): 웹소켓 서버, 연결 핸들러, API 서버, 위치 정보 캐시, 위치 이동 이력 DB, 사용자 DB, 레디스 펍/섭, 채널, 발행·구독, 서비스 탐색, 해시 링(안정 해시), 활성·비활성 사용자, TTL
- 교재 밖 기술 예시: Kafka, NATS, RabbitMQ, Erlang/Elixir, Redis Streams, SSE, MQTT, TimescaleDB·InfluxDB

## 1장 근접성 서비스와 다른 점

| 축 | 1장 근접성 서비스 | 2장 주변 친구 |
|---|---|---|
| 위치 | 사업장 주소는 거의 안 바뀜 | 친구 위치는 몇십 초마다 바뀜 |
| 트래픽 | 읽기 위주 | 쓰기와 푸시(팬아웃) 위주 |
| 통신 | REST, 클라이언트가 요청 (pull) | 웹소켓, 서버가 밀어 줌 (push) |
| 핵심 | 공간 색인 | 위치 변경 전파(펍/섭), 유상태 서버 확장 |

## 1. 요구사항 (교재 기준안)

- 기능: 주변 친구 목록(거리, 마지막 갱신 시각 포함), 몇 초마다 목록 갱신
- 비기능: 낮은 지연, 안정성(일부 유실 허용), 결과적 일관성(사본이 원본과 맞기까지 몇 초는 괜찮다)
- 규모 가정: 반경 5마일, 30초 갱신(걷는 속도 시속 3~4마일), DAU 1억, 동시 접속 = DAU의 10% = 1,000만, 1인 평균 친구 400명, 친구 상한 5,000명, 양방향 친구 관계만
- 위치 갱신 QPS = 1,000만 / 30 ≈ **33.4만**
- 팬아웃 = 33.4만 × 400 × 10%(반경 안 활성 친구) ≈ **1,400만 건/초**

## 2. 초안 설계

### P2P를 쓰지 않는 이유
이론적으로는 단말끼리 직접 주고받을 수 있다. 하지만 모바일 단말은 연결이 불안정하고 전력이 부족하다. 그래서 공용 백엔드를 둔다.
백엔드의 일: 활성 사용자의 위치 변경을 받아 → 반경 안 활성 친구의 단말에 전달한다. 반경 밖이면 보내지 않는다.

### 개략적 설계 (그림 2.5)
- **로드밸런서**: RESTful API 서버와 웹소켓 서버 앞단
- **RESTful API 서버(무상태)**: 친구 추가·삭제, 사용자 정보 갱신 등 부가 작업. 요청/응답
- **웹소켓 서버(유상태)**: 친구 위치 변경을 거의 실시간으로 처리. 클라이언트는 한 대와 연결을 유지. 접속 시 반경 안 친구 위치도 이 서버가 보낸다
- **위치 정보 캐시(레디스)**: 활성 사용자의 최신 위치. 항목에 TTL이 있어서 만료되면 비활성으로 간주하고 삭제된다. 위치를 갱신하면 TTL도 갱신된다
- **위치 이동 이력 DB**: 위치 이력 저장(주변 친구 표시와 직접 관련은 없음, ML 등 부가 용도)
- **사용자 DB**: 사용자 정보, 친구 관계
- **레디스 펍/섭**: 초경량 메시지 버스. 채널 생성이 매우 싸서 수백만 개 채널을 만들 수 있다(기가바이트급 메모리). 메시지는 저장되지 않고 구독자에게 전달되면 사라진다

### 위치 변경 전파 (그림 2.6, 2.8)
- 사용자마다 **전용 채널** 1개. 그 사용자의 친구들과 연결된 웹소켓 연결 핸들러가 구독자다.
- 흐름: 사용자 1 위치 변경 → 연결된 웹소켓 서버 → 사용자 1 채널에 발행 → 구독자(친구들의 핸들러)에게 브로드캐스트 → 핸들러가 거리 재계산 → 반경 안이면 갱신된 위치와 시각을 친구 단말에 전송
- 거리 필터는 **구독 측 핸들러**가 한다(핸들러가 자기 사용자의 위치를 변수로 들고 있다).

### API
| # | API | 프로토콜 | 방향 | 요청 | 응답 |
|---|---|---|---|---|---|
| ① | 웹소켓 초기화 | WS | 앱 → 서버 | 위도·경도·시각 | 반경 안 친구들 위치 |
| ② | 주기적 위치 갱신 | WS | 앱 → 서버 | 위도·경도·시각 | 없음 |
| ③ | 친구 위치 변경 수신 | WS | 서버 → 앱 | — | 친구 위치·변경 시각 |
| ④ | 새 친구 구독 | WS | 앱 → 서버 | 친구 ID | 친구 최신 위치·시각 |
| ⑤ | 구독 해지 | WS | 앱 → 서버 | 친구 ID | 없음 |
| ⑥ | 친구 추가·삭제 등 | HTTP | 앱 → API 서버 | 친구 ID 등 | 성공 여부 |

- 위치를 아는 건 단말(GPS)뿐이라 위치 전송 API가 2개다(접속 시 1번 + 주기적으로).
- ⑥이 성공하면 앱의 콜백이 웹소켓으로 ④/⑤를 보낸다.

### 데이터 모델
- **위치 정보 캐시**: 키 `user_id` → 값 `{위도, 경도, 시각}`. 최신 위치 하나만 필요하고 영속성이 중요하지 않다(캐시가 날아가도 다음 갱신에 다시 채워진다). 그래서 DB가 아니라 레디스를 쓴다.
- **위치 이동 이력 DB**: `user_id, latitude, longitude, timestamp`. 쓰기가 압도적이고 수평 확장이 필요하다 → **Cassandra**. RDB도 가능하지만 한 대로는 부족해 사용자 ID로 샤딩해야 한다.

## 3. 규모 확장 설계

### API 서버
- 무상태. CPU 사용률, 부하, I/O 상태에 따라 자동 확장한다.

### 웹소켓 서버
- 사용률에 따라 자동 확장하는 것 자체는 어렵지 않다. 다만 **유상태**라 노드를 내릴 때 주의한다.
- 노드를 내리기 전에 로드밸런서에서 **draining** 상태로 표시해 새 연결을 받지 않게 하고, 기존 연결이 모두 끊긴 뒤 내린다. 새 버전 배포도 같은 방식으로 한다.

### 클라이언트 초기화 (보충)
1. 위치 정보 캐시에 내 위치 갱신(TTL 시작)
2. 연결 핸들러 변수에 내 위치 저장
3. 사용자 DB에서 친구 목록 조회
4. 위치 정보 캐시에서 친구들 위치 일괄 조회. TTL이 만료된 비활성 친구는 캐시에 없다
5. 친구마다 거리 계산 → 반경 안이면 친구 위치와 시각을 앱으로 전송
6. 친구 **전원**의 채널 구독(활성·비활성 무관). 비활성 친구 채널은 메모리만 조금 쓰고 메시지가 없으니 CPU를 쓰지 않는다
7. 내 채널에 내 위치 발행

### 사용자 DB (보충)
- 사용자 정보와 친구 관계. 한 대로는 부족하니 사용자 ID 기준으로 샤딩한다(RDB 또는 NoSQL).
- 규모가 크면 이 데이터는 별도 팀이 관리하고, 내부 API로만 접근하는 경우가 많다.

### 위치 정보 캐시 (보충)
- 크기: 동시 접속 1,000만 × 약 100B ≈ **1GB** → 메모리는 한 대로 충분하다.
- 하지만 초당 33.4만 쓰기는 레디스 한 대가 감당하기 무겁다 → 사용자 ID 기준으로 **샤딩**한다.
- 가용성을 위해 샤드마다 대기 노드로 복제한다. 주 노드가 죽으면 대기 노드로 빠르게 넘긴다.

### 레디스 펍/섭 서버 (보충)
- **메모리**: 주변 친구 기능을 쓰는 사용자 1억 명에게 채널 하나씩. 사용자당 평균 구독 친구 100명, 구독자 포인터 20B → 1억 × 100 × 20B ≈ **200GB** → 100GB 서버 2대면 된다.
- **CPU**: 초당 1,400만 push. 보수적으로 서버 한 대가 초당 10만 구독자에게 push 한다면 → **140대**.
- 결론: 병목은 메모리가 아니라 **CPU(네트워크 push)**. 한 대로는 불가능하고 분산 클러스터가 필요하다.

### 레디스 펍/섭 서버 클러스터
- **서비스 탐색 컴포넌트**(etcd, ZooKeeper): 해시 링 같은 소규모 설정을 보관한다. 웹소켓 서버는 해시 링으로 발행·구독할 펍/섭 서버를 고른다. 해시 링 사본을 웹소켓 서버에 둘 수 있으나 원본과 동기화하는 장치가 필요하다.
- 채널 배치: `hash(채널)` → 해시 링에서 시계 방향 첫 서버.
- **무상태 관점**: 메시지는 저장되지 않고 전달되면 사라진다. 이 관점이면 위험과 비용이 낮다.
- **유상태 관점(실제)**: 펍/섭 서버는 채널별 구독자 정보를 들고 있다. 서버를 교체하거나 해시 링에서 빼면 채널을 다른 서버로 옮기고, 모든 구독자에게 알려 새 서버의 채널을 다시 구독하게 해야 한다.
  - 클러스터 크기를 바꾸면 많은 채널이 다른 서버로 옮겨 가고 **재구독 요청이 폭주**한다. 그 사이 위치 갱신 메시지가 유실될 수 있다.
  - 그래서 혼잡 시간 트래픽을 감당하도록 **넉넉히 미리 확보**(오버 프로비저닝)하고, 크기 조정은 **부하가 가장 낮은 시간**에 한다.
- **장애 대응**: 장애 시 온콜 경보 → 서비스 탐색의 해시 링에서 장애 노드를 대기 노드로 교체 → 모든 웹소켓 서버에 통지 → 각 연결 핸들러가 구독 중인 채널 중 장애 노드에 있던 채널만 새 노드로 재구독. 교체되는 서버의 채널만 손보고 대규모 이동을 피한다.

### 친구 추가·삭제
- 친구를 추가하면 앱에 등록한 콜백이 웹소켓 서버에 "새 친구 채널 구독"을 보낸다. 삭제도 콜백으로 구독 해지를 보낸다.

### 친구가 아주 많은 사용자
- 친구 상한(페이스북 5,000명)과 양방향 관계만 가정한다.
- 수천 명을 구독하는 관계는 많은 웹소켓 서버에 흩어져 있어 핫스팟이 생기지 않는다.
- 친구가 많은 사용자의 채널이 있는 펍/섭 서버는 부하가 조금 더 크지만, 펍/섭 서버가 100대 넘게 있고 헤비 유저 채널이 고루 흩어져 있어 특정 서버가 크게 부담을 지지는 않는다.

### 주변의 임의 사용자 (그림 2.12, 2.13)
- 지오해시 격자마다 채널을 하나씩 둔다. 격자 안 사용자는 그 채널을 구독한다.
- 위치가 바뀌면 핸들러가 지오해시를 계산해 해당 격자 채널에 발행한다.
- 격자 경계 사용자를 위해 내 격자 + 주변 격자 채널도 구독한다.

### 레디스 펍/섭의 대안
- **Erlang/Elixir**: BEAM 프로세스가 매우 가볍다(사용자당 프로세스 하나, 수백만 개 가능). 분산 구독이 내장돼 있어 레디스 펍/섭을 대체할 수 있다. 다만 전문 인력을 구하기 어렵다.

## 최종 흐름 (교재)

### 접속 초기화
위의 "클라이언트 초기화" 1~7단계.

### 주기적 위치 갱신
1. 앱이 위치를 로드밸런서로 전송
2. 로드밸런서가 그 앱과 연결된 웹소켓 서버로 전달
3. 웹소켓 서버가 위치 이동 이력 DB에 저장
4. 위치 정보 캐시 갱신(TTL 연장), 핸들러 변수 갱신
5. 내 채널에 발행
6. 채널을 구독한 친구들의 핸들러가 수신
7. 각 핸들러가 친구 ↔ 나 거리를 재계산
8. 반경 안이면 갱신된 위치와 시각을 친구 앱으로 푸시. 밖이면 보내지 않는다

## 시나리오별로 교재 기준안이 흔들리는 지점

| 시나리오 | 교재 가정이 깨지는 곳 | 검토할 만한 대안 |
|---|---|---|
| S1 동네친구 | 규모가 1/5. 140대가 아니라 10대 수준 | 교재 구조를 축소하되, 단일 리전·적은 노드라 장애 한 대의 영향 비율이 크다. 연말 피크용 오버 프로비저닝 |
| S2 글로벌 프렌즈 | 친구가 다른 대륙, 데이터 거주 규제 | 지역별 클러스터 + 지역 간 친구 위치는 해당 지역 경유 또는 공유 제한. 증설은 저부하 시간대에 점진적으로 |
| S3 같이달려 | 5초 주기, 연속 유실 불가, 이력이 핵심 기능 | 이력 저장 경로를 메시지 큐(Kafka) → Cassandra로 분리, 클라이언트 보간, 크루 채널 하나로 전파. 거대 크루는 채널 분할 또는 샘플링 |
| S4 지금여기 | 친구 그래프 없음, 밀집 격자 | 지오해시 채널 + 인접 격자 구독, 밀집 격자는 더 작은 격자나 샘플링(최대 50명 표시), 흐린 위치는 발행 전에 처리 |
