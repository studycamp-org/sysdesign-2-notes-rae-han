## 1. 요구사항 (교재 기준안)

- 기능: 사용자 위치 갱신, 경로 안내 서비스(ETA 포함), 지도 표시
- 비기능: **높은 정확도**(잘못된 길 안내 금지), **부드러운 경로 안내**(지도 표시·확대가 끊기지 않음), **낮은 데이터·배터리 사용량**, 일반적인 가용성·확장성
- 규모 가정: DAU 10억, 1인 주당 35분 경로 안내 → 주당 350억 분 → **하루 50억 분**
- 위치 갱신 QPS: 1초마다 보내면 50억 × 60 / 10⁵ ≈ **300만** → 15초 묶음이면 **20만**, 피크(× 5) **100만**
- 지도 타일 저장: 4²¹ ≈ 4.4조 장 × 100KB ≈ 440PB → 지구 표면 90%가 무인 지역이라 80~90% 압축 → ≈ 50PB → 확대 수준 합 50 × 4/3 ≈ **67PB**
- 도로 데이터: 외부 원본 수 TB, 경로 안내 타일로 변환해도 비슷한 규모. 메타데이터는 무시할 만큼 작다.

## 2. 개략적 설계

### 지도 101
- **지오코딩**: 주소 → 위도·경도. 역지오코딩은 반대. 인터폴레이션으로 GIS 데이터와 결합해 도로망을 좌표 공간에 대응시킨다.
- **지오해싱**: 영역을 4개 격자로 재귀 분할(00, 01, 10, 11)해 짧은 문자열로 표현. 지도 타일을 식별하는 키로 쓴다.
- **지도 타일**: 클라이언트는 화면에 필요한 타일만 받아 모자이크처럼 붙인다. 확대 수준마다 다른 타일 묶음. 확대 수준 0 = 세계 전체 256 × 256 한 장, 한 단계 올릴 때마다 동서 × 2, 남북 × 2(확대 수준 1은 2 × 2 = 512 × 512, 2는 4 × 4 = 1024 × 1024). 21단계.
- **경로 안내 알고리즘**: 다익스트라 또는 A\*의 변형. 교차로 = 노드, 도로 = 간선. 성능이 **그래프 크기에 민감**하다.
- **경로 안내 타일**: 지오해시처럼 격자로 나누고, 격자 안 도로망을 그래프로 변환. 각 타일은 도로로 이어진 다른 타일의 참조를 가진다. 메모리 요구량이 낮고, 한 번에 처리할 경로가 줄고, 필요한 만큼만 불러온다.
- **계층적 경로 안내 타일**: 상(작은 타일, 지방도) / 중(관할구를 잇는 간선도로) / 하(가장 넓은 타일, 도시·주를 잇는 고속도로). 장거리는 출발·도착 근처만 상 계층, 중간은 하 계층으로 건너뛴다.

### 위치 서비스
- 클라이언트가 위치 이력을 **버퍼에 모아 15초 정도마다 일괄 전송**. `POST /v1/locations`, `locs` = `(위도, 경도, 시각)` 배열.
- 쓰기가 압도적이므로 쓰기에 강하고 확장이 쉬운 **Cassandra**. **HTTP keep-alive**와 함께 사용.
- 위치 스트림의 가치: 실시간 교통 모니터링, 새 도로·폐쇄 도로 탐지, 개인화, 더 정확한 ETA와 교통에 따른 경로 변경.

### 경로 안내 서비스
- A → B의 합리적으로 빠른 경로. `GET /v1/nav?origin=...&destination=...` → 거리, 소요 시간, 경로(polyline), 단계별 안내.
- 참고: 실제 Google Routes API는 `POST https://routes.googleapis.com/directions/v2:computeRoutes` + JSON 본문 + 필수 필드 마스크(`X-Goog-FieldMask`). 응답 `routes[]`에 `distanceMeters`, `duration`(교통 반영), `staticDuration`(미반영), `polyline`, `legs[].steps[]`.

### 지도 표시
- 선택지 1 즉석 생성: 서버 클러스터에 심각한 부하, 캐시 어려움. 선택지 2 **미리 만든 타일**: 정적이라 CDN 캐시 효율, 규모 확장, 성능 모두 유리. 원본은 객체 저장소, 사본은 CDN.
- 같은 길을 반복해 다니므로 **클라이언트 캐시**가 데이터 사용량을 크게 줄인다.
- 데이터 사용량: 30km/h, 타일 1장 200m × 200m(100KB) → 1km × 1km = 25장 = 2.5MB → 시간당 75MB, **분당 1.25MB**.
- CDN 트래픽: 50억 분 × 1.25MB = **6.25PB/일** → 6.25PB / 10⁵ ≈ **62,500MB/s** → POP 200개면 POP당 ≈ 300MB/s.
- 타일 URL: 위치 + 확대 수준 → 지오해시 → `https://cdn.map-provider.com/tiles/9q9hvu.png`.
  - 클라이언트 계산: 왕복 없음. 대신 플랫폼마다 구현, 인코딩 방식을 오래 유지해야 함.
  - 서버 계산(**지도 타일 서비스**): 위치·확대 수준 → 타일 URL 집합. 바꾸기 쉬움(그림 3.12: 사용자 → 로드밸런서 → 지도 타일 서비스가 URL 생성 → 사용자가 CDN에서 다운로드).

## 3. 상세 설계

### 데이터
| 데이터 | 저장 | 이유 |
|---|---|---|
| 경로 안내 타일 | S3 같은 객체 저장소에 **인접 리스트**로, 지오해시 기준 분류. 직렬화해 지역 캐시 | 메모리에 두기엔 너무 많고, DB에 넣기엔 비용이 아깝고 DB 기능을 쓸 일이 없다 |
| 사용자 위치 | Cassandra. 키 `user_id`(파티션) + `timestamp`(클러스터링), 값 위도·경도, `user_mode`, `driving_mode` | 쓰기 많음, AP(위치는 금방 낡아 일관성보다 가용성) |
| 장소(지오코딩 DB) | 레디스 같은 키-값 | 읽기 빈번, 쓰기 드묾 |
| 미리 만든 지도 이미지 | 객체 저장소 + CDN | 정적, 대용량 |

- **경로 안내 타일 처리 서비스**: 외부 사업자·기관의 도로 + 메타데이터를 주기적으로 변환. 다른 타일로 이어지는 도로는 그 타일 참조를 포함.

### 위치 데이터 활용 (그림 3.15)
- 위치 서비스가 DB에 쓰면서 **카프카**로 스트리밍 → 실시간 교통 상황 서비스(교통량 DB), 개인화 ML 서비스(개인화 DB), 경로 안내 타일 처리 서비스(새 도로·폐쇄 탐지 → 객체 저장소 타일 갱신), 분석 서비스(분석 DB).

### 지도 표시 (상세)
- 미리 만든 래스터 타일: 단순, CDN에 유리. 확대 시 픽셀이 깨지고 단계 전환이 부드럽지 않다.
- **벡터 타일**: WebGL로 경로·다각형을 클라이언트가 그림. 이미지보다 압축률이 월등(데이터 사용량↓), 확대가 매끄럽다.

### 경로 안내 서비스 (상세)
- **지오코딩 서비스**: 주소 → 위도·경도.
- **경로 계획 서비스**: 현재 교통·도로 상태를 반영해 최적 경로를 만드는 오케스트레이터.
- **최단 경로 서비스**: 출발지·목적지 좌표 → **상위 k개 최단 경로**. 교통은 고려하지 않고 도로 구조만 → 결과 **캐시 유리**. 지오해시로 출발·도착 타일을 찾고, 그래프를 탐색하며 필요한 타일을 객체 저장소(또는 캐시)에서 가져온다. 다른 확대 수준 타일로도 연결된다. 경로가 충분해질 때까지 범위를 넓힌다.
- **ETA 서비스**: 후보 경로별 소요 시간. ML로 현재 교통 + 이력에서 **앞으로 10~20분**을 예측.
- **순위 결정 서비스**: 사용자 필터(유료 도로·고속도로 제외 등) 적용 후 ETA 순으로 상위 k개.
- **갱신 서비스**: 카프카 위치 스트림을 구독해 실시간 교통 DB와 경로 안내 타일을 비동기 갱신.
- **적응형 ETA 및 경로 변경 서비스**:
  - 경로 안내 중인 활성 사용자를 추적하고, 교통이 바뀌면 ETA·경로를 다시 알린다.
  - 단순 방식: `user_1: r_1, r_2, ..., r_k`(경로의 모든 상 계층 타일) → 타일이 바뀔 때 전 사용자 레코드를 훑어야 함(O(n)).
  - 개선(그림 3.20): `user_1: r_1, super(r_1), super(super(r_1)), ...` — 출발지와 목적지를 모두 포함하는 타일까지 재귀적으로 상위 타일을 보관. 바뀐 타일이 레코드 **마지막 타일**에 속하는 사용자만 대상.
  - 교통이 다시 좋아지면: 이용 가능한 경로들의 ETA를 주기적으로 재계산해 더 빠른 경로를 알린다.
  - 전송 프로토콜: 모바일 푸시(메시지 크기 제한 iOS 4,096바이트, 웹 미지원) / 롱 폴링 / **웹소켓**(롱 폴링보다 서버 부담 적고 양방향 — 배송이 목적지에 가까워질 때 같은 양방향 통신에도 대응) / SSE(단방향).

### 최종 설계안 (그림 3.21)
- 모바일 사용자 → 경로 안내 서비스 → {지오코딩 서비스 → 지오코딩 DB}, {경로 계획 서비스 → 순위 결정(→ 필터링) / 최단 경로(→ 경로 안내 타일 객체 저장소) / ETA(→ 교통량 DB)}, {적응형 ETA 및 경로 변경 → 교통량 DB, 활성 사용자}. 실시간 교통 상황 서비스 → 교통량 DB, 위치 DB.

## 시나리오별로 교재 기준안이 흔들리는 지점

| 시나리오 | 교재 가정이 깨지는 곳 | 검토할 만한 대안 |
|---|---|---|
| S1 길동무 | 규모가 작다(피크 4만 QPS, 지도 2.5GB/s). 국내 도로만 | 서비스 지역 그래프가 작아 계층을 2단계로 줄이거나 사전 계산 기법도 가능. 출퇴근 ETA 정확도가 핵심이라 시간대별 이력 비중을 높인다. 돌발은 우회로 쏠림(같은 우회로 30만 명) |
| S2 월드맵 | 교재 수치 그대로, 대륙 간 장거리, 데이터 요금 민감 | 교재 기준안 + 벡터 타일로 데이터 절감. 돌발(대규모 도로 단절 + 동시 요청)은 최단 경로 캐시 무효화와 재계산 폭주 → 교통 DB에서 폐쇄 도로 비용 무한대로 즉시 반영, 요청 우선순위·속도 제한 |
| S3 번개배달 | 5초·묶음 없음, 고객에게 위치 팬아웃, 다중 경유지 | 라이더 위치를 웹소켓으로 받고 펍/섭(2장)으로 고객에게 전파. 경유지 순서 최적화(TSP 근사), 오토바이 전용 도로 비용(골목·단지). 재계산 요청 속도 제한 |
| S4 산길 | 통신 불가, 오프라인 지도, 교통 대신 경사 | 지역 단위 오프라인 패키지(벡터) + 단말 내 경로 탐색, 위치는 기기 저장 후 일괄 업로드(끊겼다 붙을 때 폭주 → 지터). 폐쇄 정보는 작은 델타 패치로 따로 배포. 돌발은 패키지 사전 다운로드 유도·CDN 프리워밍 |
