# 질문 은행 (6문항, 20~30분)

**핵심 질문은 정확히 6개다.** 질문당 약 3~4분. 묶음 질문은 소항목 최대 2개.
교재의 나머지 주제(지도 투영법, 지오코딩 원리, 지도 타일 저장 용량 계산, 지오코딩 DB, 순위 결정·필터링, 최종 흐름 서술)는 질문으로 내지 않는다.
답에 나오면 기록하고, 아키텍처와 핵심 흐름은 마무리 단계에서 진행자가 그린다.

| 단계 | 질문 |
|---|---|
| 요구사항 | Q1 규모 추정 |
| 초안 설계 | Q2 지도 표시 방식 (묶음) · **Q3 경로 탐색 방식 ★** · Q4 위치 갱신과 저장 (묶음) |
| 상세 설계 | **Q5 적응형 ETA 및 경로 변경 (돌발)** · Q6 교통 반영과 경로 안내 타일 갱신 (묶음) |

각 항목: **질문** / **선택지**(예시, 다른 답도 받음) / **꼬리 질문**(빈약하거나 충돌할 때만, 최대 1회) / **좋은 근거의 신호**(피드백 기준, 답하기 전에는 보여주지 않음).

시나리오별 계산 정답 (진행자 확인용, 하루 ≈ 10⁵초, 지도 데이터 분당 1.25MB):

| 시나리오 | 하루 경로 안내(분) | 위치 갱신 QPS (1초 전송) | 위치 갱신 QPS (시나리오 전송 방식) | 피크 QPS | 지도 데이터 트래픽 |
|---|---|---|---|---|---|
| S1 | 2,000만 × 70 / 7 = **2억** | 2억 × 60 / 10⁵ = 12만 | 15초 묶음 → **8,000** | × 5 = **4만** | 2억 × 1.25MB = 250TB/일 ≈ **2.5GB/s** |
| S2 | 10억 × 35 / 7 = **50억** | 50억 × 60 / 10⁵ = 300만 | 15초 묶음 → **20만** | × 5 = **100만** | 6.25PB/일 ≈ **62.5GB/s**, POP 200개면 POP당 ≈ 300MB/s |
| S3 | 20만 × 480 ≈ **1억** | 1억 × 60 / 10⁵ = 6만 | 5초·묶음 없음 → 6만 / 5 ≈ **1.2만** | × 4 ≈ **5만**. 고객 push는 × 3 ≈ 피크 15만/s | 1억 × 1.25MB = 125TB/일 ≈ **1.25GB/s** |
| S4 | 100만 × 180 = **1.8억** | 1.8억 × 60 / 10⁵ ≈ 11만 | 기기에 쌓았다 올림 → 15초 묶음 가정 시 **7,200** (끊겼다 붙을 때 몰려 올라옴) | × 4 ≈ **3만** | 국립공원 1곳: 500km² / (0.2km)² = 12,500장 × 100KB ≈ **1.25GB** (저확대 포함 × 4/3 ≈ 1.7GB). 돌발 시 1만 명 × 1.7GB ≈ **17TB** 동시 다운로드 |

(교재 S2 저장 용량: 4²¹ ≈ 4.4조 장 × 100KB ≈ 440PB → 무인 지역 압축 후 ≈ 50PB → 전 확대 수준 합 ≈ **67PB**. 질문으로 내지 않고 Q1·Q2 꼬리 질문에서만 쓴다.)

## 요구사항

### Q1. 규모 추정
- **질문**: 하루 경로 안내 시간(분), 위치 갱신 QPS(1초 전송일 때 / 시나리오 전송 방식일 때 / 피크), 경로 안내 중 지도 데이터 트래픽을 직접 계산하세요. 이 서비스의 가장 큰 트래픽은 무엇인가요?
- **좋은 근거의 신호**: 하루 분 = DAU × 주당 분 / 7. 1초 전송 QPS = 하루 분 × 60 / 10⁵. 묶어 보내면 주기로 나눈다(15초면 1/15). 위치 갱신은 **쓰기**가 압도적이고, 지도 타일은 **읽기**지만 정적이라 CDN이 받는다. 경로 안내 요청 자체는 상대적으로 드물다. 두 숫자가 서로 다른 계층(위치 서비스 vs CDN)을 압박한다는 걸 짚는다.
- **꼬리 질문**: "위치를 1초마다 보내면 QPS가 몇 배가 되나요? 그 대가로 무엇을 얻나요?" / "지도 타일 트래픽을 서버가 직접 받으면 어떻게 되나요?"

## 초안 설계

### Q2. 지도 표시 방식 (묶음)
- **질문**:
  1. 지도는 어떤 형태로 클라이언트에 보내나요? A) 요청마다 서버가 즉석에서 그림 B) 확대 수준별로 미리 만든 래스터 타일 + CDN C) 벡터 타일 + 클라이언트 렌더링(WebGL) D) 조합(예: 저확대 래스터 + 고확대 벡터) E) 지역 단위 오프라인 패키지
  2. 화면에 필요한 타일 URL은 누가 계산하나요? A) 클라이언트가 위치·확대 수준으로 지오해시를 계산 B) 서버의 지도 타일 서비스가 URL 집합을 내려줌 C) 표준 z/x/y 타일 좌표 D) 그 밖
- **좋은 근거의 신호**: 즉석 렌더링은 서버 클러스터에 심각한 부하, 캐시 불가. 미리 만든 타일은 정적이라 CDN 캐시 효율이 높고 규모 확장이 쉽다. 벡터는 압축률이 좋아 **데이터 사용량이 적고** 확대가 매끄럽지만 클라이언트 렌더링 부담이 있다. 같은 길을 반복해 다니므로 **클라이언트 캐시**도 데이터 사용량을 크게 줄인다. URL을 클라이언트가 계산하면 왕복이 없지만 플랫폼마다 구현해야 하고 인코딩 방식을 오래 바꾸기 어렵다. 서버가 계산하면 요청 1회가 늘지만 바꾸기 쉽다(그림 3.12).
- **꼬리 질문**: "이미 배포된 앱 수억 대가 지오해시로 URL을 만들고 있는데 타일 인코딩을 바꿔야 한다면요?" / "벡터로 바꾸면 Q1의 지도 데이터 트래픽은 어떻게 달라지나요? 대신 무엇이 늘어나나요?"

### Q3. 경로 탐색 방식 ★핵심
- **질문**: 출발지 → 목적지의 빠른 경로를 어떻게 찾나요? 도로 데이터를 어떤 형태로 두고, 어떤 알고리즘을 어디서 돌리나요?
- **선택지**: A) 전 세계(또는 서비스 지역) 도로를 그래프 하나로 메모리에 올려 다익스트라/A\* B) 지오해시처럼 격자로 나눈 **경로 안내 타일** + 필요한 타일만 로드하는 A\* 변형 C) **계층적 경로 안내 타일**(상: 지방도 / 중: 간선도로 / 하: 고속도로) D) 사전 계산 기법(Contraction Hierarchies 등, 교재 밖) E) 외부 API(Routes API 등) 사용
- **좋은 근거의 신호**: 경로 탐색 알고리즘은 **그래프 크기에 민감**하다 → 통째로는 메모리·시간이 감당 안 된다. 경로 안내 타일은 인접 리스트로 객체 저장소(S3)에 두고 지오해시로 찾으며, 각 타일은 도로로 이어진 다른 타일을 참조한다. 장거리는 출발·도착 근처만 상 계층, 중간은 하 계층(고속도로) 타일로 건너뛴다. **최단 경로(도로 구조만, 캐시 가능)와 ETA(교통 반영, 실시간)를 분리**하면 각자 다른 속도로 갱신할 수 있다. 시나리오의 경로 비용(S3 경유지 순서, S4 경사)을 반영한다.
- **세부 질문** (고른 방식에 맞는 것 **하나만**, 같은 질문 안에서):
  - **그래프 하나**: "서비스 지역 도로가 노드 수억 개면 메모리에 몇 GB가 필요하고, 경로 1건 탐색은 몇 개 노드를 방문하나요?"
    - 신호: 국내(S1)는 가능할 수도 있다는 판단은 근거가 될 수 있다. 다만 탐색 범위가 넓어지면 지연이 커지고, 서버마다 전체 그래프를 들고 있어야 한다.
  - **경로 안내 타일**: "타일 크기는 무엇으로 정하나요? 타일 경계를 넘는 도로와, 필요한 타일을 불러오는 시점(미리 / 탐색 중)은요?"
    - 신호: 다른 타일로 이어지는 도로는 그 타일 참조를 포함한다. 탐색하면서 필요한 타일을 객체 저장소(또는 캐시)에서 가져오고, 경로가 충분히 나올 때까지 범위를 넓힌다.
  - **계층적 타일**: "몇 계층으로, 각 계층에 어떤 도로를 넣나요? 상 계층에서 하 계층으로 언제 갈아타나요?"
    - 신호: 교재는 3계층. 출발지 타일에서 시작해 상위 계층 타일로 연결되는 지점을 통해 갈아탄다. 계층 사이 연결 정보가 타일에 있어야 한다.
  - **사전 계산**: "도로가 바뀌거나(공사·폐쇄) 교통으로 가중치가 바뀌면 사전 계산을 얼마나 다시 하나요?"
    - 신호: 쿼리는 매우 빠르지만 가중치 변경에 약하다 → 최단 경로(구조)에만 쓰고 교통은 ETA 단계에서 반영하는 분리와 잘 맞는다.
  - **외부 API**: "호출 비용과 쿼터, 교통 데이터·ETA 품질을 우리가 통제하지 못하는 점은 괜찮나요?"
    - 신호: 초기에는 합리적. 핵심 기능(ETA 정확도)을 외부에 맡기는 위험을 안다.
- **꼬리 질문**:
  - 그래프 하나: "서울 → 부산 경로를 찾을 때 강원도 산길 노드까지 방문하지 않게 하려면요?"
  - 타일(계층 없음): "서울 → 부산이면 상 계층 타일을 몇 장 불러와야 하나요?"
  - 계층적 타일: "고속도로가 막혀서 지방도가 더 빠를 때도 하 계층만 보면 놓치지 않나요?"
  - 공통: "최단 경로 결과를 캐시해도 되나요? 교통이 바뀌면 그 캐시는 어떻게 되나요?"

### Q4. 위치 갱신과 저장 (묶음)
- **질문**:
  1. 클라이언트는 위치를 어떻게 보내나요? 주기·묶음 여부와 프로토콜을 정하세요. A) 1초마다 즉시 B) 기기에 모아 15~30초마다 묶어서(HTTP keep-alive) C) 이동 속도·상황에 따른 적응형 D) 웹소켓으로 계속
  2. 위치 데이터는 어디에, 어떤 키로 저장하고 누가 쓰나요? A) RDB B) 쓰기에 강한 키-값·열 중심 DB(Cassandra 등) C) 메시지 큐(Kafka)에 흘리고 소비자가 각자 저장 D) 조합
- **좋은 근거의 신호**: 묶음 전송은 QPS와 **배터리·데이터 사용량**을 같이 줄인다(꽉 막힌 도로에선 자주 보낼 필요가 없다). 위치는 금방 낡으므로 일관성보다 **가용성**(CAP의 AP) → Cassandra. 키는 `user_id`(파티션 키) + `timestamp`(클러스터링 키) → 사용자별 최근 위치와 시간 범위 조회가 빠르다. DB에 쓰는 것과 동시에 **카프카로 스트리밍**해 교통 상황·경로 안내 타일 갱신·개인화·분석이 각자 소비한다(그림 3.15). 시나리오의 실시간 요구(S3 고객 추적)와 끊김(S4)을 반영한다.
- **꼬리 질문**: "15초 묶음이면 경로 이탈을 서버가 최대 몇 초 늦게 알게 되나요? 그건 괜찮나요?" / "교통 상황 서비스가 위치 DB를 직접 폴링하면 무엇이 문제인가요?"

**▶ 초안 설계 체크포인트**

## 상세 설계

### Q5. 적응형 ETA 및 경로 변경 (돌발 상황 포함)
- **질문**: 먼저 시나리오 카드의 **돌발 상황**을 제시하고, 그 상황을 전제로 답하게 한다.
  - 어떤 타일의 교통 상황이 바뀌었을 때, **영향받는 사용자**를 어떻게 빨리 찾고, 어떤 방식으로 알리나요? 찾기: A) 활성 사용자 전부를 훑으며 경로 확인 B) 사용자별로 경로가 지나는 모든 타일 목록 저장 C) 현재 타일 → 상위 타일 → … 출발지·목적지를 모두 포함하는 타일까지 재귀적으로 저장(그림 3.20) D) 타일 → 사용자 역인덱스. 알리기: 모바일 푸시 / 롱 폴링 / SSE / 웹소켓
  - 돌발 상황 때문에 앞의 결정 중 바꿀 것이 있나요?
- **좋은 근거의 신호**: 활성 사용자 n명을 매번 훑으면 O(n)이고, 사용자별 전체 타일 목록은 레코드가 길다. 재귀 수집은 레코드의 **마지막(가장 큰) 타일에 바뀐 타일이 속하는지**만 먼저 보면 대부분을 빠르게 걸러낸다. 역인덱스는 조회가 빠르지만 사용자가 움직일 때마다 갱신 비용이 있다. 교통이 **다시 좋아졌을 때**도 주기적으로 대안 경로 ETA를 재계산해 더 빠른 길을 알려야 한다. 모바일 푸시는 메시지 크기 제한(iOS 4,096바이트), 웹소켓은 롱 폴링보다 서버 부담이 적고 양방향, SSE는 단방향. 돌발에서는 **재계산 폭주**(수십만 명 동시)를 줄이는 방법(우선순위, 공통 우회 경로 공유, 점진 알림)을 본다.
- **꼬리 질문**: "30만 명에게 동시에 같은 우회로를 알려주면 그 우회로는 어떻게 되나요?" / "사용자가 계속 움직이면 그 사용자의 타일 기록은 언제 다시 계산하나요?"

### Q6. 교통 반영과 경로 안내 타일 갱신 (묶음)
- **질문**:
  1. ETA는 무엇으로 계산하나요? A) 현재 교통 속도만 B) 과거 같은 요일·시간대 이력 C) 현재 + 이력으로 앞으로 10~20분을 기계학습 예측 D) 그 밖(시나리오 고유 비용: 경사, 들를 곳 수 등)
  2. 도로가 새로 열리거나 닫히면 경로 안내 타일은 어떻게 갱신하나요? A) 외부 도로 데이터로 주기적 배치 재생성만 B) 위치 스트림으로 새 도로·폐쇄 도로를 탐지해 비동기 갱신 C) 타일은 그대로 두고 교통 DB에서 해당 도로 비용을 무한대로 D) 조합. 갱신된 타일을 캐시한 서버들에는 어떻게 반영하나요?
- **좋은 근거의 신호**: 교재는 ML로 현재 교통과 이력에서 **앞으로 10~20분**을 예측한다(출발 시점이 아닌 도착 시점의 교통이 중요). 타일은 인접 리스트로 S3에 두고 직렬화해 **지역 캐시**에서 서빙하므로, 갱신 시 캐시 무효화(버전 키, TTL)가 필요하다. 구조 변화(새 도로)는 타일 갱신, 일시 통제는 교통 DB로 처리하는 분리가 깔끔하다. 위치 스트림을 쓰는 갱신 서비스는 카프카를 구독해 비동기로 반영한다.
