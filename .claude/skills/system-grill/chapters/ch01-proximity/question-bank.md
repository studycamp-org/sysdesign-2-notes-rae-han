# 질문 은행 (7문항, 20~30분)

**핵심 질문은 정확히 7개다.** 질문당 약 3분. 묶음 질문은 소항목 최대 2개.
교재의 나머지 주제(비기능 우선순위, 위치 데이터 보호, 지역·가용성 구역, 결과 필터링, 최종 흐름 서술)는 질문으로 내지 않는다.
답에 나오면 기록하고, 아키텍처와 핵심 흐름은 마무리 단계에서 진행자가 그린다.

| 단계 | 질문 |
|---|---|
| 요구사항 | Q1 규모 추정 · Q2 반영 시점과 반경 정책 (묶음) |
| 초안 설계 | Q3 API와 서비스 구조 (묶음) · **Q4 공간 색인 ★** · Q5 저장소와 색인 저장 (묶음) |
| 규모 확장 | **Q6 DB 확장 (돌발)** · Q7 캐시 (묶음) |

각 항목: **질문** / **선택지**(예시, 다른 답도 받음) / **꼬리 질문**(빈약하거나 충돌할 때만, 최대 1회) / **좋은 근거의 신호**(피드백 기준, 답하기 전에는 보여주지 않음).

시나리오별 계산 정답 (진행자 확인용):

| 시나리오 | 평균 검색 QPS | 피크 검색 QPS | 쓰기 참고 |
|---|---|---|---|
| S1 | 1,000만×10 / 10⁵ = 1,000 | ≈5,000 | 낮음 |
| S2 | 1억×5 / 10⁵ = 5,000 | 지역 단위 2~3배 | 낮음 |
| S3 | 300만×8 / 10⁵ = 240 | ≈2,400 (축제 구역 집중) | 위치 변경 20만×4 / 10⁵ ≈ 8/s, 축제 때 순간 급증 |
| S4 | 800만×12 / 10⁵ = 960 | 저녁 2~3배 | 새 판매글 반영 5분 |

(1일 ≈ 10⁵초 근사. 86,400으로 계산해도 맞다고 본다.)

## 요구사항

### Q1. 규모 추정
- **질문**: 시나리오 수치로 평균·피크 검색 QPS를 직접 계산하세요. 읽기 위주인가요, 쓰기 위주인가요? 피크 때 무엇이 먼저 병목이 될까요?
- **좋은 근거의 신호**: 1일 ≈ 10⁵초. 피크 배수 반영. 읽기가 압도적이고 쓰기가 드물다는 점은 복제 지연과 캐시 정합성을 느슨하게 가져갈 근거가 된다. 데이터 크기(사업장 수 × 행 크기)도 함께 보면 Q6 판단이 쉬워진다.
- **꼬리 질문**: "이 QPS는 DB 한 대로 버틸 수 있나요? 무엇이 먼저 병목이 될까요?"

### Q2. 반영 시점과 반경 정책 (묶음)
- **질문**:
  1. 사업장 정보 변경은 검색에 언제까지 반영되어야 하나요? A) 실시간(초) B) 수 분 이내 C) 다음날 일괄 D) 항목별로 다르게
  2. 검색 반경은 어떻게 받고, 결과가 너무 적은 지역은 어떻게 하나요? A) 고정 선택지 B) 자유 입력 C) 가까운 순 k개 D) 기본 반경 + 부족하면 자동 확장
- **좋은 근거의 신호**: 반영 시점은 기술이 아니라 비즈니스(사업자 경험, 사용자 피해)에서 출발하고, Q4 색인 갱신과 Q7 캐시 무효화를 결정한다. 고정 반경은 정밀도 종류를 줄여 색인·캐시를 단순하게 한다. k개 기준은 쿼드트리와 잘 맞는다. 자동 확장은 지연과 반경 약속 위반이라는 비용이 있다.
- **꼬리 질문**: "다음날 반영이면 폐업한 가게가 하루 동안 검색되는 건 괜찮나요?" / "반경 5km에 사업장이 3개뿐인 지역 사용자에게는 무엇을 보여주나요?"

**▶ 요구사항 체크포인트**

## 초안 설계

### Q3. API와 서비스 구조 (묶음)
- **질문**:
  1. 주변 검색 API 형태와, 결과가 많을 때(밀집 지역)의 페이지 분할 방식은? A) offset/limit B) 커서 C) 상위 N개만 D) 지도 화면 영역 단위 재요청
  2. 주변 검색(LBS)과 사업장 정보 관리를 A) 한 서비스로 B) 나눠서
- **좋은 근거의 신호**: `GET /v1/search/nearby?latitude&longitude&radius`. 목록에는 최소 정보, 상세는 `GET /v1/businesses/:id`. 거리순 정렬에서 offset은 위치가 조금만 바뀌어도 결과가 밀린다. LBS는 읽기 전용·무상태라 수평 확장이 쉽고, 사업장 서비스는 쓰기 QPS가 낮아 트래픽 패턴이 다르다. 분리하면 운영이 복잡해진다는 비용도 인정한다.
- **꼬리 질문**: "걸어가면서 2페이지를 요청하면 1페이지와 중복되거나 빠지는 결과는 없나요?" / "나누면 LBS는 가게 이름과 사진을 어디서 가져오나요?"

### Q4. 공간 색인 ★핵심
- **질문**: "주변 사업장 찾기"를 어떤 방식으로 구현할까요?
- **선택지**: A) 위도·경도 각각 인덱스 + 범위 질의 B) 균등 격자 C) 지오해시 D) 쿼드트리 E) 구글 S2 F) R-트리(PostGIS 등) G) 조합
- **좋은 근거의 신호**: 인덱스는 1차원에서만 효율적이라 2차원을 1차원으로 대응시켜야 한다. 시나리오의 밀도 편차, Q2 반경 정책과 반영 시점, 불규칙 경계(S4)와 연결한다.
- **세부 질문** (고른 방식에 맞는 것 **하나만**, 같은 질문 안에서):
  - **지오해시**: "반경별 지오해시 길이를 정하고, 내 위치가 칸 모서리에 있을 때 옆 칸 가게가 빠지는 문제는 어떻게 하나요?"
    - 신호: 0.5km→6(1.2×0.6km), 1·2km→5(4.9×4.9km), 5·20km→4(39×19.5km). 공통 접두어가 없는 인접 위치, 내 칸 + 인접 8칸 조회 후 실제 거리로 필터·정렬.
  - **쿼드트리**: "이 시나리오의 사업장 수로 메모리를 계산하고, 사업장이 바뀌면 여러 LBS 서버의 트리를 어떻게 갱신하나요?"
    - 신호: 말단 = 사업장 수/100, 내부 ≈ 말단×1/3, 말단 832B, 내부 64B. 교재 2억 ≈ 1.71GB, S1 ≈ 25MB, S3 ≈ 4MB, S4 ≈ 125MB. 갱신은 점진(서버 간 일시 불일치) / 다음날 일괄(캐시 대량 무효화) / 실시간(락으로 복잡). 구축에 수 분 → 점진 배포.
  - **S2**: "셀 레벨(최소/최대/최대 셀 수)을 어떻게 정하고, 행정동 경계는 어떻게 표현하나요?"
    - 신호: 힐베르트 곡선이라 인접성이 유지된다. 영역 지정으로 경계 폴리곤을 셀 집합으로 덮는다. 경계가 바뀌면 커버링을 다시 계산한다.
  - **2차원 검색 / 균등 격자**: 꼬리 질문으로 대신한다.
  - **그 밖의 기술**: "이 QPS와 갱신 빈도에서 이 기술의 한계와 대응책은?"
- **꼬리 질문**:
  - 2차원 검색: "위도 범위 결과와 경도 범위 결과가 각각 수백만 건이면 교집합 비용은요?"
  - 균등 격자: "강남역 칸과 산간 칸의 사업장 수 차이는 어떻게 하나요?"
  - 지오해시: "강남역에서 정밀도를 고정하면 칸 하나에 몇 개가 들어갈까요?"
  - 쿼드트리: "Q2에서 정한 반영 시점을 트리 갱신 방식으로 맞출 수 있나요?"
  - S2: "S2를 다뤄본 팀원이 없으면 학습·운영 비용은요?"

### Q5. 저장소와 색인 저장 (묶음)
- **질문**:
  1. 사업장 데이터를 어디에 둘까요? A) RDB 주-부 B) RDB + PostGIS C) NoSQL D) Elasticsearch geo E) Redis GEO F) 조합
  2. 색인은 어떻게 저장하나요? (지오해시·S2) A) 칸 1행에 사업장 ID JSON 배열 B) (geohash, business_id) 복합 키로 사업장마다 1행 / (쿼드트리) 트리를 만들 원본을 어디서 읽나요?
- **좋은 근거의 신호**: 읽기가 압도적이라 읽기 사본으로 확장한다. 사업장 데이터는 관계형이고 작다. Q2에서 빠른 반영을 골랐다면 복제 지연이 쟁점이다. JSON 배열은 통째로 읽고 써야 하고 동시 수정에 락이 필요하다. 복합 키 행은 추가·삭제만 하면 되고, `LIKE 'prefix%'`로 상위 정밀도도 조회할 수 있다.
- **꼬리 질문**: "두 사장님이 같은 칸에 동시에 등록하면 JSON 배열 방식에서는 무슨 일이 생기나요?" / "주 DB에 쓴 직후 사본에서 읽으면 이전 데이터가 보입니다. Q2와 맞나요?"

**▶ 초안 설계 체크포인트**

## 규모 확장

### Q6. DB 확장 (돌발 상황 포함)
- **질문**: 먼저 시나리오 카드의 **돌발 상황**을 제시하고, 그 상황을 전제로 답하게 한다.
  - 사업장 테이블과 색인 데이터를 각각 어떻게 확장할까요? A) 읽기 사본 증설 B) 사업장 ID 샤딩 C) 지역 샤딩 D) 지금은 필요 없음(크기·QPS로 판단)
  - 돌발 상황 때문에 앞의 결정 중 바꿀 것이 있나요?
- **좋은 근거의 신호**: 데이터 크기를 먼저 계산한다. 사업장 테이블은 ID 샤딩이 고르게 퍼지고 운영이 쉽다. 색인은 작아서 한 서버에 들어가니 사본 증설이 단순하고, 지오해시 샤딩은 핫스팟과 경계 문제로 까다롭다. 데이터 거주(S2)라면 지역 분리가 정당화된다.
- **꼬리 질문**: "지역이나 지오해시 기준으로 샤딩하면 강남(서울) 샤드만 뜨거워지지 않나요?"

### Q7. 캐시 (묶음)
- **질문**:
  1. 캐시가 정말 필요한가요? 둔다면 키와 값은? A) 사용자 위도·경도 B) 지오해시/셀 ID → 사업장 ID 목록 C) 사업장 ID → 사업장 정보 D) 요청 파라미터 해시 / 필요 없다면 대안(사본 몇 대?)은?
  2. 사업장 정보가 바뀌면 캐시를 어떻게 맞추나요? A) TTL만 B) 쓰기 시 무효화 C) write-through D) 야간 배치 E) 변경 이벤트로 비동기 무효화
- **좋은 근거의 신호**: "정말 필요한가?" 자체를 묻는다(벤치마킹, 비용). 모바일 좌표는 부정확해 키로 부적합하고 격자 ID가 맞다. 두 종류의 키-값(칸 → ID 목록, ID → 정보). 용량 8B × 사업장 수 × 정밀도 종류 수(교재 ≈ 5GB, S1 ≈ 72MB). 무효화는 **Q2 반영 시점과 일치**해야 한다. 위치가 바뀐 사업장은 이전 칸과 새 칸 키를 모두 무효화한다. 일괄 무효화는 캐시 스탬피드를 부른다.
- **꼬리 질문**: "Q2에서 수 분 이내를 골랐는데 TTL 1일이면 모순 아닌가요?" / "가게가 A칸에서 B칸으로 옮기면 어떤 키들이 영향을 받나요?"

**▶ 규모 확장 체크포인트 → 마무리**
