# 학습 내용 요약 (진행자 참고용)

출처: 「가상 면접 사례로 배우는 대규모 시스템 설계 기초 2」 1장 근접성 서비스, 스터디 정리본
(https://github.com/SPRING-STUDY-2023/System-Design-Interview2).
`힌트` 응답, 피드백, 결과 문서의 "교재와 다르게 간 곳" 섹션에 쓴다. 답하기 전에 기준안을 먼저 말하지 않는다.

## 용어와 교재 밖 기술

- 용어(교재 표기): 사업장, LBS(위치 기반 서비스), 지오해시, 쿼드트리, 구글 S2, 정밀도, 인접 격자, 주-부 복제, 읽기 사본
- 교재 밖 기술 예시: PostGIS(R-트리), Redis GEO, Elasticsearch geo_point, Uber H3, MongoDB 2dsphere

## 설계의 흐름

1. **요구사항**: 기능 요구사항, 그리고 지연·가용성·데이터 보호 같은 비기능 요구사항과 규모 추정
2. **초안 설계**: API, 데이터 모델, DB, 알고리즘 같은 기본 기술 결정
3. **규모 확장 설계**: 실제 서비스 범위를 고려한 가용성·확장성·지역 배치 등 인프라 결정

## 1. 요구사항 (교재 기준안)

- 기능: 위치와 반경으로 주변 사업장 검색 / 사업장 정보 추가·삭제·갱신(실시간 반영 불필요, 다음날 반영) / 사업장 상세 조회
- 비기능: 낮은 응답 지연, 데이터 보호(위치는 민감 정보), 고가용성과 규모 확장성(밀집 지역 피크)
- 규모: DAU 1억, 사업장 2억, 1인 하루 5회 검색 → 1억 × 5 / 10⁵ ≈ **5,000 QPS**

## 2. 초안 설계

### API
- `GET /v1/search/nearby` — latitude, longitude, radius(선택, 기본 5,000m). 응답: `{ total, businesses: [...] }`
- 사업장: `GET/POST/PUT/DELETE /v1/businesses/:id`
- 페이지 분할이 필요하다. 검색 결과에는 목록용 최소 정보만 담고 상세는 별도 API로 조회한다.

### 데이터 모델
- 읽기가 압도적(검색, 상세 조회). 쓰기(사업장 편집)는 드물다.
- 그래서 읽기 위주 → RDB 주-부 구성이 적합하다.
- 테이블: business(사업장 정보), geospatial index(위치 색인)

### 개략적 설계
- **로드밸런서**: 단일 DNS 진입점. URL 경로로 서비스 라우팅
- **LBS(위치 기반 서비스)**: 읽기 전용, QPS 높음, 무상태라 수평 확장이 쉬움
- **사업장 서비스**: 쓰기는 QPS 낮음, 조회는 특정 시간대에 QPS 높음
- **DB 클러스터**: 주(쓰기) → 사본(읽기) 복제. 실시간 반영이 필요 없으니 복제 지연은 문제가 아님
- 클라우드라면 여러 리전과 AZ에 배치하고 시간대별로 자동 확장한다

### 주변 검색 알고리즘

| 방안 | 핵심 | 장점 | 단점 |
|---|---|---|---|
| 2차원 검색 | 위도·경도 BETWEEN 범위 질의 | 직관적 | 인덱스는 1차원만 효율적. 각 차원 결과가 거대해 교집합 비용이 큼 |
| 균등 격자 | 지도를 같은 크기 칸으로 분할 | 단순 | 사업장 분포가 불균등. 인접 칸 찾기가 까다로움 |
| 지오해시 | 위경도를 비트 교차 → base32 문자열. 접두어가 같으면 같은 칸 | 구현 쉬움. 색인 갱신 쉬움(행 하나 추가·삭제) | 정밀도를 고정하면 칸 크기도 고정(밀도 적응 불가). 격자 가장자리 이슈 |
| 쿼드트리 | 칸 안의 사업장이 기준(예: 100개) 이하가 될 때까지 재귀 4분할. 메모리 자료구조 | 밀도에 따라 칸 크기가 바뀜. k개 최근접 검색에 유리 | 구현과 갱신이 까다로움(O(log n) 순회, 멀티스레드 락, 리밸런싱). 서버 시작 시 구축 시간 |
| 구글 S2 | 힐베르트 곡선으로 1차원 색인. 곡선상 인접 = 1차원상 인접 | 다단계 셀. 지오펜스(임의 경계). 영역 지정(최소/최대 레벨, 최대 셀 수) | 학습 곡선, 설명 난이도 |
| R-트리 | 경계 사각형 계층 트리(PostGIS 등) | DB가 직접 지원 | 교재에서는 자세히 다루지 않음 |

해시 기반: 균등 격자, 지오해시, 카르테시안 계층 / 트리 기반: 쿼드트리, S2, R-트리

사용 현황: 지오해시(Bing 지도, Redis, MongoDB, Lyft), 쿼드트리(Yext), 지오해시 + 쿼드트리(Elasticsearch), S2(구글 맵, Tinder)

#### 지오해시 세부
- 전 세계를 사분면으로 나눈다: 위도 [-90,0]→0, [0,90]→1 / 경도 [-180,0]→0, [0,180]→1. 이를 재귀적으로 반복한다. 12단계(길이 = 정밀도).
- 예: 구글 본사 `9q9hvu`, 페이스북 본사 `9q9jhr` (접두어 `9q9`를 공유)
- 최적 정밀도는 반경으로 그린 원을 덮는 최소 크기 칸을 만드는 길이다.

| 반경 | 지오해시 길이 | 칸 크기 |
|---|---|---|
| 0.5km | 6 | 1.2km × 0.6km |
| 1km | 5 | 4.9km × 4.9km |
| 2km | 5 | 4.9km × 4.9km |
| 5km | 4 | 39km × 19.5km |
| 20km | 4 | 39km × 19.5km |

- 가장자리 이슈 1: 아주 가까운데 공통 접두어가 전혀 없는 경우(적도·본초 자오선 양쪽). 그래서 단순한 `LIKE 'prefix%'`로는 놓친다.
- 가장자리 이슈 2: 접두어는 길게 같지만 다른 칸에 있는 경우. 인접 8칸까지 가져와 해결한다.
- 결과 부족: 반경 안 결과만 반환하거나, 지오해시 길이를 줄여(칸 확대) 검색 반경을 키운다.

#### 쿼드트리 세부
- 말단 노드 832B(좌표 32B + ID 8B × 100), 내부 노드 64B(좌표 32B + 자식 포인터 32B)
- 2억 사업장 기준: 말단 200만, 내부 ≈ 67만 → 약 **1.71GB**. 서버 한 대 메모리에 들어간다. 읽기가 많으면 여러 서버에 복제한다.
- 구축 시간 O(n/100 · log(n/100)). 2억 기준 수 분.
- 검색: 루트에서 출발점이 속한 말단까지 내려간다. 사업장이 부족하면 인접 노드를 추가한다.
- 운영: 서버 시작 시 구축하므로 한 번에 많은 서버에 배포하지 않는다(점진 배포, 블루-그린).
- 갱신: 점진 갱신(서버 간 일시적 불일치) / 다음날 일괄(캐시 대량 무효화로 부하) / 실시간(락 때문에 복잡). 리밸런싱은 말단 구간을 넉넉히 잡아 완화한다.
- 교재 결론: 서버 간 일시적 불일치는 받아들이고 사업적으로 푼다. 사용량이 적은 시간대에 정상화한다.

## 3. 규모 확장 설계

### DB
- **사업장 테이블**: 샤딩 후보. 사업장 ID 기준이면 부하가 고르게 퍼지고 운영이 쉽다.
- **지리 색인 테이블**
  - 방법 1: 지오해시 → 사업장 ID JSON 배열 1행. 갱신할 때 배열 전체를 읽고 써야 하고 동시성 제어에 락이 필요하다.
  - 방법 2(추천): (geohash, business_id) 복합 키로 1행씩. 추가·삭제가 쉽고 락이 필요 없다.
  - 확장: 색인 데이터는 작아서 한 서버에 다 들어간다. 읽기 부하는 **사본 증설**로 푼다(교재 추천). 샤딩은 로직이 까다롭다.
  - 데이터 크기를 보지 않고 샤딩을 정하는 건 섣부르다.

### 캐시
- 먼저 "캐시가 정말 필요한가?"를 묻는다. 사본 증설로 풀 수도 있다. 벤치마킹과 비용 분석이 필요하다.
- 캐시 키: 사용자 좌표는 부적합(모바일 위치는 부정확하고 미세하게 바뀜). 지오해시나 쿼드트리 칸 ID처럼 위치가 조금 바뀌어도 같은 값이어야 한다.
- 데이터 유형: ① 지오해시 → 칸 안의 사업장 ID 목록 ② 사업장 ID → 사업장 정보 객체
- 조회: 캐시 → 없으면 `SELECT business_id FROM geohash_index WHERE geohash LIKE '{geohash}%'` → 캐시에 저장(예: TTL 1일)
- 용량: 8B × 2억 × 3가지 정밀도(4, 5, 6) ≈ **5GB**. 서버 한 대로 충분하다. 지연과 가용성을 위해 지역별로 복제한다.
- 갱신: 다음날 반영으로 합의했으므로 밤사이 작업으로 갱신한다. 추가·수정·삭제 시 DB 갱신 후 캐시 무효화도 가능하다.

### 지역 및 가용성 구역
- 사용자와 물리적 거리를 줄인다. 인구에 따라 트래픽을 분산한다(밀집 지역은 별도로 빼거나 AZ를 여럿 쓴다). 지역별 사생활 보호법을 준수한다.

### 결과 필터링 (시간대, 업종)
- 격자로 좁히면 후보 수가 적다. 근처 사업장 ID를 확보한 뒤 상세 정보를 가져와 필터링하면 된다.

### 최종 검색 흐름 (교재)
1. 클라이언트가 위치와 반경을 LB로 전송
2. LB → LBS
3. LBS가 반경에 맞는 지오해시 길이 계산
4. 내 지오해시 + 인접 8개 목록 생성
5. 각 지오해시로 "지오해시" Redis에서 사업장 ID 조회
6. "사업장 정보" Redis에서 상세 정보 조회 → (거리 계산·정렬) → 응답

### 사업장 조회·수정 흐름 (교재)
- 조회: 사업장 정보 Redis → 없으면 DB → 캐시에 저장 후 반환
- 수정: 주 DB 쓰기 → 다음날 반영 합의 → 캐시는 야간 작업으로 갱신

## 시나리오별로 교재 기준안이 흔들리는 지점

| 시나리오 | 교재 가정이 깨지는 곳 | 검토할 만한 대안 |
|---|---|---|
| S1 동네맛집 | 밀도 편차가 극단적(강남 vs 산간) | 지오해시 + 결과 부족 시 확장, 또는 쿼드트리. 핫스팟 캐시 |
| S2 글로벌 트립 | 자유 반경, 데이터 거주 | 정밀도 계산 로직 또는 S2/쿼드트리. 지역 격리 배치, 지역 기준 데이터 분리 |
| S3 트럭맵 | 다음날 반영 → 1분 반영 | 갱신이 쉬운 지오해시 + 복합 키 행 갱신, 이전 칸·새 칸 캐시 무효화, 짧은 TTL, 이벤트 기반 갱신. 쿼드트리는 갱신 비용이 큼 |
| S4 우리동네 | 원형 반경 → 불규칙 행정동 경계, 지오펜스 | S2 셀 커버링, 경계 변경 시 커버링 재계산 |
