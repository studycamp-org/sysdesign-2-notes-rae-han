# 시나리오 카드

각 시나리오는 교재 기준안(텍스트 메시지 KB 단위 / 여러 소비자 그룹 / 파티션 안 순서 보장 / 2주 보관 / 전달 방식 설정 가능 / 사본 3개 + ISR / 생산자 클라이언트 라이브러리의 버퍼·라우팅 / 풀 모델 + 소비자 그룹 코디네이터)과
일부러 다른 제약을 하나 이상 넣어서, 같은 질문이라도 다른 선택이 정당화되도록 만들었다.

목록을 보여줄 때는 `한 줄 요약`만 보여준다. 고른 뒤에 카드 전체를 보여준다.

계산 공통 가정(카드에 따로 없으면): 하루 ≈ 10⁵초, 사본 3개, **파티션 1개가 감당하는 쓰기 처리량 ≈ 10MB/s**, 1KB = 10³바이트로 어림한다.
파티션 수는 **처리량 기준**(피크 MB/s ÷ 10MB/s)과 **소비자 병렬성 기준**(피크 메시지/s ÷ 소비자 1명 처리 속도) 중 큰 값이다. 같은 그룹 안에서 파티션 하나는 소비자 하나만 읽기 때문이다.

---

## S1. 로그창고 — 서버 로그·지표 수집  (입문 / 교재와 가장 비슷함)

**한 줄 요약**: 서버 1만 대의 로그와 지표를 모아 검색·이상 탐지·장기 보관으로 흘려보낸다. 처리량이 최우선이고 약간의 손실은 괜찮다.

| 항목 | 값 |
|---|---|
| 생산자 | 서버 1만 대의 로그 수집 에이전트 |
| 메시지 | 평균 **50만 건/s**, 건당 **1KB** (텍스트 로그 한 줄) |
| 피크 | 평균의 **3배** (배포·장애 시) |
| 보관 | **2주** (교재와 같음) |
| 소비자 그룹 | 3개: 검색 색인, 실시간 이상 탐지, 장기 보관(객체 저장소 적재) |
| 소비자 1명 처리 속도 | 약 **1만 건/s** (묶어서 색인) |
| 손실 허용 | 로그 일부(0.1% 이하) 유실은 괜찮다. 대신 생산자(서비스 서버)가 느려지면 안 된다 |
| 순서 | 같은 서버의 로그는 대략 순서대로면 충분 |

**설계 포인트**: 교재가 말한 "높은 대역폭 vs 낮은 지연" 중 대역폭 쪽으로 끝까지 밀어도 되는 시나리오. 손실 허용이 ACK와 전달 방식을 어디까지 내려도 되는지 정한다.

**돌발 상황**: "대형 장애가 나서 30분 동안 로그가 평소의 10배로 쏟아집니다. 이상 탐지 소비자 그룹이 따라가지 못해 지연(lag)이 20분까지 벌어졌고, 정작 장애 분석에 필요한 최근 로그를 못 보고 있습니다. 무엇을 바꾸나요?"

## S2. 안전결제 — 주문·결제 이벤트  (정확성 / 소비자 병렬성 변형)

**한 줄 요약**: 쇼핑몰의 주문 생성 → 결제 승인 → 배송 요청 이벤트. 유실도 중복 결제도 안 되고, 같은 주문의 이벤트는 순서가 지켜져야 한다.

| 항목 | 값 |
|---|---|
| 생산자 | 주문 서비스, 결제 서비스 |
| 메시지 | 평균 **2만 건/s**, 건당 **2KB** (주문 ID, 금액, 상태) |
| 피크 | 평균의 **5배** (특가 행사 시작 직후) |
| 보관 | **30일** (분쟁 확인용. 그 뒤는 별도 아카이브) |
| 소비자 그룹 | 결제 승인, 배송 요청, 정산·회계 |
| 소비자 1명 처리 속도 | 건당 **20ms** (외부 PG사 호출) → 1명이 약 **50건/s** |
| 손실 허용 | **0건**. 중복 결제도 0건 |
| 순서 | **같은 주문**의 이벤트는 반드시 생성 → 승인 → 취소 순서 |

**설계 포인트**: 처리량은 작지만 소비자 한 명이 느려서 **파티션 수가 소비자 병렬성으로 결정**된다. 교재의 "전달 방식은 설정 가능" 가정에서 정확히 1회를 실제로 고르면 무슨 값을 치르는지 본다.

**돌발 상황**: "결제 승인 소비자 한 대가 PG사 승인을 받은 직후, 오프셋을 커밋하기 전에 죽었습니다. 재조정이 끝날 때까지 30초 동안 그 파티션 소비가 멈췄고, 새로 배정된 소비자가 같은 메시지를 다시 읽습니다. 고객은 결제가 두 번 될까요?"

## S3. 라이브톡 — 라이브 방송 채팅·알림  (낮은 지연 / 핫 파티션 변형)

**한 줄 요약**: 라이브 방송의 채팅과 실시간 알림을 푸시 서버로 넘긴다. 지연이 생명이고 오래 보관할 필요는 없다.

| 항목 | 값 |
|---|---|
| 생산자 | 채팅 API 서버 |
| 메시지 | 평균 **20만 건/s**, 건당 **200바이트** (짧은 채팅) |
| 피크 | 평균의 **4배** (인기 방송 시작) |
| 보관 | **1일** (교재보다 짧음. 다시보기용 채팅만) |
| 소비자 그룹 | 웹소켓 푸시 서버, 금칙어 필터, 다시보기 적재 |
| 소비자 1명 처리 속도 | 약 **2만 건/s** |
| 지연 목표 | 생산 → 시청자 화면 **p99 200ms 이내** |
| 순서 | 같은 방송 채팅방 안에서는 순서대로 보여야 한다 |

**설계 포인트**: 교재가 기본으로 잡은 "일괄 처리로 대역폭 확보"가 지연 목표와 부딪힌다. 방송(채팅방)을 키로 쓰면 인기 방송 하나가 파티션 하나에 몰린다.

**돌발 상황**: "구독자 500만 명인 스트리머가 방송을 시작해 채팅방 하나에 메시지가 평소의 50배 몰립니다. 그 방송을 맡은 파티션의 리더 브로커 CPU가 100%가 됐고, 같은 브로커에 있던 다른 방송들의 채팅까지 늦어집니다. 어떻게 하나요?"

---

## S4. 달리는차 — 커넥티드카 텔레메트리, 두 지역 운영  (다중 데이터 센터 변형)

**한 줄 요약**: 차량 100만 대가 10초마다 상태를 보낸다. 서울과 부산 두 데이터 센터에서 운영하고, 한쪽이 통째로 죽어도 데이터를 잃으면 안 된다.

| 항목 | 값 |
|---|---|
| 생산자 | 차량 100만 대, **10초마다** 1건 |
| 메시지 | 건당 **500바이트** (위치, 속도, 배터리, 고장 코드) |
| 피크 | 평균의 **3배** (출퇴근) + 터널·지하주차장을 나온 차들이 쌓인 데이터를 **한꺼번에** 올림 |
| 보관 | **90일** (고장 분석·보험 분쟁) |
| 소비자 그룹 | 고장 감지(실시간), 운행 기록 적재, 분석 |
| 소비자 1명 처리 속도 | 약 **5,000건/s** |
| 운영 | 서울·부산 **두 데이터 센터**. 데이터 센터 간 왕복 지연 약 10ms |
| 손실 허용 | 고장 코드는 0건. 위치는 일부 유실 허용 |

**설계 포인트**: 교재가 "사본은 여러 데이터 센터에 분산하는 것이 안전하지만 동기화가 어렵고 지연·비용이 늘어난다"고 넘어간 부분을 직접 결정해야 한다. 한 토픽 안에서도 데이터마다 손실 허용이 다르다.

**돌발 상황**: "서울 데이터 센터가 정전으로 통째로 내려갔습니다. 차량들은 부산으로 붙기 시작했고, 서울에서 고장 감지 소비자가 마지막으로 커밋한 오프셋은 부산 클러스터의 오프셋과 번호가 다릅니다. 고장 감지는 어디서부터 다시 읽나요?"

## 직접 만들기

다음 항목을 사용자와 함께 채워서 카드를 만든다. 빈 칸은 진행자가 그럴듯한 값을 제안하고 동의를 받는다.

- 서비스 성격(로그·지표 / 업무 이벤트 / 실시간 메시징 / IoT) / 생산자 종류와 수
- 초당 메시지 수, 메시지 크기, 피크 배수 / 보관 기간
- 소비자 그룹 목록과 소비자 1명 처리 속도
- 손실 허용(있음/없음), 중복 허용, 순서 보장 범위(전체 / 키별 / 상관없음)
- 지연 목표 / 데이터 센터 수
- 돌발 상황 1개 (진행자가 만들되, 시나리오의 가장 약한 가정을 깨는 것으로)

## 랜덤

S1~S4 중 하나를 무작위로 고른다. 입문자라면 S1을 권한다.
