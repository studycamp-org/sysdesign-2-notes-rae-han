## 0. 왜 메시지 큐인가

- 결합도 완화, 규모 확장성 개선, 가용성 개선(한 컴포넌트에 장애가 나도 다른 컴포넌트는 큐와 계속 상호작용), 성능 개선(비동기 통신, 응답을 기다리지 않고 전송).
- **메시지 큐 vs 이벤트 스트리밍 플랫폼**: 전통적 메시지 큐(RocketMQ, ActiveMQ, RabbitMQ, ZeroMQ)는 메시지를 소비자가 가져가면 지우고, 보관을 보증하지 않으며, 대개 소비 순서를 보장하지 않는다. 이벤트 스트리밍 플랫폼(카프카, 펄사)은 오래 보관하고 여러 번 읽을 수 있다. 이 장의 설계는 **둘을 합친 쪽**(보관 + 순서 + 여러 소비자).

## 1. 요구사항 (교재 기준안)

- 기능: 생산자는 메시지를 큐에 보내고 소비자는 큐에서 가져간다 / **여러 소비자가 같은 메시지를 받을 수 있다** / **생산된 순서대로 소비** / **데이터 보관 2주** / 메시지 크기는 KB 수준(텍스트만) / 전달 방식은 최대 한 번·최소 한 번·정확히 한 번 중 **설정 가능**.
- 비기능: 로그 수집 같은 용도를 위한 **높은 대역폭**과 전통적 큐 용도의 **낮은 지연**을 설정으로 고를 수 있다 / 규모 확장성(메시지 양 급증 대응) / **지속성·내구성**(디스크에 보관, 여러 노드에 복제).
- 교재는 규모 추정 숫자를 따로 주지 않는다. 숫자는 시나리오 카드에서 받는다.

## 2. 개략적 설계

- **메시지 모델**: 일대일(메시지는 한 소비자만 가져가고, 가져갔다고 알리면 큐에서 지운다) / **발행-구독**(토픽에 보내면 토픽을 구독하는 모든 소비자에게 전달, 그림 4.4).
- **토픽, 파티션, 브로커**: 토픽 데이터가 서버 한 대로 감당이 안 되면 **파티션(=샤딩)**으로 나눈다(그림 4.5). 파티션은 클러스터의 서버(**브로커**)에 고르게 분산한다. 토픽 용량을 늘리려면 파티션 수를 늘리면 된다.
  - 파티션은 FIFO 큐처럼 동작 → **같은 파티션 안에서만 순서 보장**. 파티션 안 메시지 위치 = **오프셋**.
  - 메시지에 키(예: 사용자 ID)를 붙이면 같은 키는 같은 파티션으로. 키가 없으면 무작위.
- **소비자 그룹**(그림 4.7): 토픽을 함께 소비하는 소비자 묶음. 그룹마다 오프셋을 따로 관리(예: 과금용 그룹, 회계용 그룹). 같은 그룹 안에서는 병렬로 소비하지만 **파티션 하나는 그룹 안 소비자 하나만** 읽는다(순서 보장을 위한 제약). 그래서 그룹 안 소비자가 파티션 수보다 많으면 노는 소비자가 생긴다. 모든 소비자를 한 그룹에 넣으면 일대일 모델과 같아진다. 파티션을 미리 넉넉히 잡아 두면 처리 용량은 소비자를 추가해 늘린다.
- **개략적 설계안**(그림 4.8): 생산자 → 브로커(파티션 보관) → 소비자(그룹). 저장소는 **데이터 저장소**(메시지), **상태 저장소**(소비자 상태·오프셋), **메타데이터 저장소**(토픽 설정·속성). **조정 서비스**는 서비스 탐색(어떤 브로커가 살아 있는지)과 **리더 선출**(브로커 하나가 컨트롤러가 되어 파티션 배치를 책임짐)을 맡고, 주키퍼나 etcd를 쓴다.

## 3. 상세 설계

### 중요한 결정 세 가지
1. 회전 디스크의 높은 **순차 탐색 성능** + OS의 적극적 디스크 캐시 → 디스크 기반 자료 구조.
2. 생산자 → 큐 → 소비자로 가는 동안 **수정 없이 전송**되는 메시지 자료 구조 → 복사 비용 최소화.
3. **일괄 처리** 우선 → 작은 I/O가 많으면 대역폭이 안 나온다.

### 데이터 저장소
- 특성: 읽기·쓰기가 빈번하고 대부분 **순차적**. 갱신·삭제는 없다(보관 기간이 지난 메시지 삭제만).
- DB(관계형: 토픽별 테이블 / NoSQL: 토픽별 컬렉션)는 대규모 읽기·쓰기가 동시에 몰리는 경우를 잘 처리하기 어렵다.
- **쓰기 우선 로그(WAL)**: 새 항목을 끝에 추가만 하는 파일(MySQL 복구 로그, 주키퍼도 사용). 오프셋 = 로그 위치. 파일을 **세그먼트**로 나눠 활성 세그먼트에만 쓰고, 한계에 닿으면 새 세그먼트를 연다. 이전 세그먼트는 읽기만 하고, 보관 기간이 지나거나 용량 한계면 통째로 지운다. 폴더 구조는 `Partition-{:partition_id}/세그먼트-N`(그림 4.10).
- 디스크는 **무작위 접근일 때** 느리다. 순차 접근 + RAID 구성 + OS 페이지 캐시로 충분히 빠르다.

### 메시지 자료 구조 (표 4.1)
- `key`(byte[]), `value`(byte[], 페이로드), `topic`(string), `partition`(integer), `offset`(long), `timestamp`(long), `size`(integer), `crc`(integer, 순환 중복 검사로 무결성 확인).
- 키가 없으면 파티션은 무작위, 있으면 `hash(key) % numPartitions`. 키는 파티션 결정용이며 업무 데이터와는 별개.

### 일괄 처리
- 여러 메시지를 한 번의 네트워크 요청으로 → 왕복 비용 감소. 더 큰 순차 쓰기 → 디스크 대역폭 증가.
- **대역폭과 지연은 동시에 달성하기 어렵다.** 지연이 중요하면 묶음을 줄이고(디스크 효율은 떨어짐) 처리량은 **토픽당 파티션 수를 늘려** 확보. 대역폭이 중요하면 묶음을 키운다.

### 생산자 측 작업 흐름
- 초안(그림 4.11): 생산자 → **라우팅 계층**(메타데이터 저장소의 사본 분산 계획을 캐시) → 파티션의 **리더 사본**이 있는 브로커. 리더가 받으면 단순 사본들이 리더에서 가져가 동기화하고, 충분한 사본이 동기화되면 리더가 커밋하고 생산자에게 회신(그때부터 소비 가능).
- 한계: 라우팅 계층 때문에 네트워크 노드가 하나 늘어 지연 증가, 일괄 처리 고려 없음.
- 개선(그림 4.12): 라우팅 계층과 **버퍼**를 **생산자 클라이언트 라이브러리** 안으로. 네트워크를 덜 거쳐 지연 감소, 생산자가 파티션 결정 로직을 직접 가질 수 있음, 버퍼에 모았다가 일괄 전송해 대역폭 증가. 묶음 크기는 대역폭과 지연 사이의 타협.

### 소비자 측 작업 흐름
- 소비자는 특정 파티션의 오프셋을 주고 그 위치부터 이벤트를 **묶어** 가져온다(그림 4.14).
- **푸시 모델**: 장점은 낮은 지연. 단점은 소비 속도가 생산 속도보다 느리면 소비자에 큰 부하, 생산 속도에 맞는 컴퓨팅 자원이 늘 필요.
- **풀 모델**: 소비 속도를 소비자가 정한다(실시간 또는 일괄). 소비가 느리면 소비자를 늘리거나 기다리면 된다. 마지막 위치 다음을 한꺼번에 가져가 **일괄 처리에 적합**. 단점은 메시지가 없어도 계속 시도해 자원 낭비 → **롱 폴링**. 그래서 대부분의 메시지 큐는 풀 모델.
- 풀 흐름(그림 4.15): 그룹 이름을 해싱해 **그룹 전담 코디네이터 브로커**를 찾는다 → 그룹 합류·토픽 구독 → 코디네이터가 파티션 할당(라운드 로빈, 범위 기반 등) → 소비자가 파티션 리더 브로커에서 메시지 수신 → 처리 후 오프셋 갱신(상태 저장소).
- 코디네이터(소비자 그룹 조정) ≠ 조정 서비스(브로커 클러스터 조정).

### 소비자 재조정
- 어떤 소비자가 어떤 파티션을 맡을지 다시 정하는 과정. 소비자 합류·이탈·장애, 파티션 조정 때 일어난다.
- 코디네이터는 소비자 박동 메시지를 받고, 연결된 소비자 목록이 바뀌면 그룹의 **새 리더**를 뽑는다. 리더 소비자가 **파티션 배치 계획**을 만들어 코디네이터에 주면, 코디네이터가 나머지 소비자에게 알린다.
- 합류(그림 4.18): 새 소비자 합류 요청 → 기존 소비자의 다음 박동 응답으로 "다시 합류하라" → 모두 재합류 → 리더 선출 → 리더가 배치 계획 전송 → 모두 그룹 동기화로 파티션을 받는다(예: A에 1·3, B에 2·4).
- 이탈(그림 4.19): 탈퇴 요청 → 나머지 재합류 → 배치 다시 받기. 장애(그림 4.20): 박동이 끊기면 장애로 보고 재조정 시작. 재조정 동안은 소비가 멈춘다.

### 상태 저장소, 메타데이터 저장소, 주키퍼
- 상태 저장소: 소비자-파티션 배치 관계, 그룹별·파티션별 **마지막으로 소비한 오프셋**(그 앞은 모두 읽었다는 뜻). 소비자가 죽으면 새 소비자가 이 오프셋부터 이어받는다. 읽기·쓰기가 잦고 일관성이 중요 → 주키퍼 같은 키-값 저장소.
- 메타데이터 저장소: 토픽 설정·속성(파티션 수, 보관 기간, 사본 배치). 양은 적지만 일관성이 중요.
- **주키퍼**(그림 4.22): 계층적 키-값 저장소(분산 설정, 동기화, 이름 레지스트리). 메타데이터·상태 저장소와 조정 서비스를 주키퍼로 대체하면 **브로커는 데이터 저장소만** 유지하고, 브로커 리더 선출도 주키퍼가 돕는다.

### 복제
- 하드웨어 장애·영구 장애에 대비해 파티션마다 사본을 둔다(예: 사본 3개, 서로 다른 브로커). 생산자는 **리더 사본**에만 보내고, 단순 사본은 리더에서 계속 가져가 동기화. 충분한 사본이 동기화되면 리더가 회신.
- 리더 브로커(컨트롤러)가 **사본 분산 계획**을 세워 메타데이터 저장소에 둔다.
- **ISR**(동기화된 사본): 리더와 동기화된 사본. "동기화됐다"의 기준은 토픽 설정에 따른다(예: `replica.lag.max.messages = 4`면 리더와 차이가 3인 사본은 ISR). 리더는 항상 ISR.
  - 그림 4.24: 리더의 **합의 오프셋 = 13** → 그 전 메시지는 ISR 모두에 반영됨. 사본 2·3은 ISR(합의 오프셋까지 받았고 새 메시지를 가져올 수 있음), 사본 4는 따라잡지 못해 ISR 아님(따라잡으면 다시 ISR).
  - ISR은 **성능과 영속성 사이의 타협점**: 모든 사본을 기다리면 가장 안전하지만 하나만 느려도 파티션 전체가 느려진다.
- **ACK 설정**(생산자가 k개의 ISR이 받았을 때 응답 받도록 설정):
  - **ACK=all**(그림 4.25): 모든 ISR이 받은 뒤 응답. 가장 느린 ISR을 기다려 지연이 길지만 영속성 최고. 따라잡지 못한 사본은 ISR이 아니므로 기다리지 않는다.
  - **ACK=1**(그림 4.26): 리더가 저장하면 바로 응답. 응답 직후 리더에 장애가 나면 다른 사본에 반영되지 못한 메시지는 **복구할 길 없이 소실**. 낮은 지연이 중요하고 가끔 유실돼도 되는 시스템.
  - **ACK=0**(그림 4.27): 응답을 기다리지 않고 계속 보내며 재시도도 없음. 지연 최저, 손실 감수. 지표 수집·데이터 로깅.
  - ACK를 바꿀 수 있게 해 두면 성능을 위해 영속성을 일부 희생할 수 있다.
- **소비자는 리더에서 읽는다**: 설계·운영이 단순. 같은 그룹 안에서 파티션 하나는 소비자 하나만 읽으므로 리더 연결이 많지 않다. 인기 토픽이면 파티션과 소비자 수를 늘려 확장(파티션을 늘리면 리더도 여러 브로커로 흩어진다). 단, 소비자가 리더와 다른 데이터 센터에 있으면 가까운 ISR에서 읽는 선택지를 고려.

### 규모 확장성
- **생산자**: 그룹 조정이 필요 없어 추가·삭제가 쉽다.
- **소비자**: 소비자 그룹 추가·삭제는 독립적. 그룹 안 소비자 변화는 **재조정**이 처리.
- **브로커 장애 복구**(그림 4.28): 브로커 4개, 토픽 A 파티션 1 사본 = 브로커 1(리더)·2·3, 파티션 2 = 2(리더)·3·4, 토픽 B 파티션 1 = 3(리더)·4·1. 브로커 3이 죽으면 컨트롤러가 감지해 남은 브로커로 **새 분산 계획**을 만든다(A-1 → 1·2·4, A-2 → 2·1·4, B-1 → 4(새 리더)·1·2). 새 사본은 리더를 따라잡기 시작한다.
  - 고려사항: 합의로 판단할 사본 수(안전성 vs 지연) / 같은 파티션의 사본을 같은 노드에 두지 않는다 / 모든 사본이 사라지면 데이터는 영원히 사라진다 → 사본 수·위치는 안정성·비용·지연으로 정한다 / 여러 데이터 센터에 두면 안전하지만 동기화·지연·비용이 늘어난다 → **데이터 미러링**.
- **브로커 추가**(그림 4.29): 브로커 4 추가 → 컨트롤러가 파티션 2 사본을 (2, 3, 4)로 바꾸기로 결정 → 브로커 4의 새 사본이 리더에서 가져오기 시작(잠시 사본 수가 3보다 큼) → 따라잡으면 브로커 1의 불필요한 사본 삭제. 한시적으로 설정보다 많은 사본을 허용하는 것이 요령.
- **파티션 수 조정**: 토픽 규모·대역폭·가용성 때문에 바꾼다. 생산자는 브로커와 통신할 때 통지받고 소비자는 재조정 → 생산자·소비자 안정성에는 영향 없음.
  - 추가(그림 4.30): 기존 메시지는 옮기지 않는다. 이후 메시지만 늘어난 파티션 전체에 나뉜다. (보충) 키 기반이면 `hash(key) % 파티션 수`가 바뀌어 같은 키의 새 메시지가 다른 파티션으로 가므로 **키별 순서가 깨질 수 있다**.
  - 삭제(그림 4.31): (보충) 삭제할 파티션에는 새 메시지를 넣지 않고, 남은 메시지는 보관 기간이 지날 때까지 소비자가 읽을 수 있도록 남겨 둔 뒤 지운다.

### 메시지 전달 방식
- **최대 한 번**: 유실되더라도 다시 전달하지 않는다. 지표 모니터링처럼 소량 손실을 감수하는 시스템. (보충) 생산자는 ACK=0(재시도 없음), 소비자는 **처리 전에** 오프셋 커밋 → 처리 중 죽으면 그 메시지는 다시 읽히지 않는다.
- **최소 한 번**: 중복은 있을 수 있지만 유실은 없다. 중복이 문제 되지 않거나 소비자가 중복을 직접 제거할 수 있는 시스템. (보충) 생산자는 ACK=1 또는 all + 재시도, 소비자는 **처리 후에** 오프셋 커밋 → 커밋 전에 죽으면 다시 읽어 중복.
- **정확히 한 번**: 구현이 가장 까다롭고 성능·복잡도 대가가 크다. 사용자는 편하다. 지불·매매·회계 같은 금융 응용. (보충) 실무에서는 멱등 생산자 + 트랜잭션, 또는 최소 한 번 + 멱등 소비자(멱등 키, 처리 결과와 오프셋을 같은 트랜잭션에 저장)로 만든다.
